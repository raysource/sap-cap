0. 怎么用这页：一个请求的五层漏斗

排错慢，几乎都是因为跳层——页面白屏就去改注解，其实是 401；$expand 空了就去改服务，其实是 CSV 表头写错。所以先用这张漏斗把问题关进一层，再翻对应章节的表。

① 工具链：node / npm / cds CLI 能不能跑 ──▶ 第 1 节 ② 模型编译：npx cds compile 有没有 [ERROR] ──▶ 第 2 节 ③ 部署/播种：npm run deploy 有没有真的落库 ──▶ 第 2 节（CSV 行） ④ 服务运行时：请求到没到 CAP、handler 跑没跑 ──▶ 第 3 节 ⑤ 认证授权：401 还是 403、scope 对不对 ──▶ 第 4 节 ⑥ 浏览器：元数据到了没有、容器高度对不对 ──▶ 第 5 节 ⑦ 云端：构建产物、绑定、路由、配额 ──▶ 第 6 节
一句话判据 报错里有文件:行:列 → 编译期（第 2 节）；打印了 > init from … 之后失败 → 播种期（第 2 节）；有 HTTP 状态码 → 运行时/认证（第 3、4 节）；控制台/白屏 → 浏览器（第 5 节）；cf 输出 → 云端（第 6 节）。

1-1 手顺：把 Node 与原生模块（better-sqlite3）对齐

node / npmpackage.json · node_modules/better-sqlite3耗时 10 分
  1. 先固定 Node：不要用系统里的默认 Node，直接取一个 LTS 22 的路径进 PATH（示范项目 README 的实测写法）： 
    bash
    cd project-code/demo-node
export PATH="$(dirname "$(npx -y node@22 -p process.execPath)"):$PATH"
node -v                            # → v22.23.2（实测）
node -p "process.versions.modules"  # → 打印 ABI 号（127 即 Node 22 line）
  2. 看 ABI 是否与已有二进制一致：这条命令只要不抛错，就说明原生模块能加载： 
    bash
    node -e "require('better-sqlite3')" && echo bindings OK
    失败（NODE_MODULE_VERSION … 或 Could not locate the bindings file）就进入下一步；成功则跳到第 4 步。
  3. 清干净重装：ABI 不匹配时删掉 node_modules 比反复 rebuild 更省事（npm rebuild 只在 ABI 号一致、只是二进制丢了时有用）： 
    bash
    rm -rf node_modules package-lock.json
npm install                        # → added 328 packages（示范项目实测）
node -e "require('better-sqlite3')" && echo bindings OK
  4. 验证：跑一次真实建库与查询，证明二进制真的能用（不是只 import 得动）： 
    bash
    npm run deploy                     # → /> successfully deployed to db.sqlite
python3 -c "
import sqlite3; c = sqlite3.connect('db.sqlite')
print([r[0] for r in c.execute('select name from sqlite_master where type=\'table\'')])"
    期望看到 sap_training_bookorder_Books、sap_training_bookorder_Customers、sap_training_bookorder_BookOrders、sap_training_bookorder_BookOrderItems 等表（实测共 7 张，含 draft 表与 outbox 表）。
常见错误用 sudo npm install 绕过权限问题会把 node_modules 变成 root 所有，下一次安装报 EACCES；pip/nvm 混装多个 Node 时，一定要用 node -v 确认当前终端里的那一个，而不是以为「装过就有了」。

1-2 手顺：端口被占（4004/4005）时的标准处理

lsof / pkill / cds watch --portsrv 启动参数 · test/dev-proxy.js耗时 5 分
  1. 先看是谁占着（本机实测输出：node 74574 jason 12u IPv6 … TCP *:4004 (LISTEN)）： 
    bash
    lsof -nP -iTCP:4004 -sTCP:LISTEN
pgrep -fl cds-serve
  2. 结束它：确认是自己上一次留下的进程再动手；不要 kill -9，先 kill（默认 TERM）： 
    bash
    kill <PID>          # 或用进程名
pkill -f cds-serve
sleep 1 && pgrep -fl cds-serve   # 应无输出
  3. 要并行就换端口，并把下游一起改：服务端口只在一个地方定（--port 或 PORT），但代理、测试脚本、Fiori 的 dataSource 都要跟着改： 
    bash
    cds watch --port 4123                     # 服务换端口
PORT=4124 TARGET=http://localhost:4123 node test/dev-proxy.js   # 代理跟着换
  4. 验证：服务与代理各打印自己的 listening 行，且能取到元数据： 
    bash
    curl -s -o /dev/null -w '%{http_code}\n' -u alice:alice http://localhost:4123/odata/v4/book-order/$metadata   # → 200
最容易踩的自坑测试脚本里写死了 BASE=http://localhost:4004，你换了端口，脚本却不报连接错误、只报「断言失败」—— 因为它把所有请求都打到了另一个还在跑的老服务上。换端口时必须一起换脚本里的 BASE。

2. CDS 建模

这一层的错误最好排：多数会明确告诉你 文件:行:列。真正难的两类是「沉默故障」——deploy 打印成功但数据没进去 / $expand 返回空数组。它们没有报错，只能靠主动验证（查库行数、算 join 计数）才能发现。

现象（错误信息原文 / 观察）触发条件根因修复手顺如何验证
[ERROR] …:7:10: Mismatched ‘#’, expecting ‹Identifier›, ‘}’, ‘@’, ‘key’, ‘virtual’ 实体/元素里多写或错放了 #；把 enum 才用的枚举值写法用在了普通元素上 CDS 里 # 只在枚举值与注解上下文有意义，普通标识符位置不合法，解析器停在该位置 按报错的 行:列 定位并删掉多余字符；行注释必须用 //，不要用 # 或 -- npx cds compile db/schema.cds --to sql 不再打印 [ERROR]；cds watch 能启动（编译失败会以 ERR_CDS_COMPILATION_FAILURE 退出）
Mismatched ‹EOF›, expecting … 括号/大括号不配对（最常见：实体末尾少一个 }） 解析器读到文件末尾还在等闭合符号，所以位置报在文件末尾而不是出错行 在编辑器里逐个折叠顶层 entity / service 确认闭合；把文件尾部报错当作「少了一个闭合符」而不是「末尾有问题」 同上：npx cds compile … --to sql 无 [ERROR]，且打印的 CREATE TABLE 数量与实体数量一致（示范项目 db/schema.cds 是 4 张表）
SqliteError: in cds.deploy(): table sap_training_bookorder_BookOrderItems has no column named orders_ID in: + INSERT INTO … 后面跟着 /> deployment to db.sqlite failed CSV 表头写的是 CDS 元素名（或拼错），例如把 order_ID 写成 orders_ID、把 currency_code 写成 currency 种子数据的表头必须等于物理列名，不是 CDS 里的元素名；关联生成的 FK 列名是 <元素名>_<目标主键> 先用编译产物查出真列名，再改 CSV 表头：npx cds compile db/schema.cds --to sql | grep -A12 'CREATE TABLE sap_training_bookorder_BookOrderItems'；然后 npm run deploy 同一条命令改回 order_ID 后 deploy 成功；再查行数：python3 连 db.sqlite 统计明细行（期望 BookOrderItems 9 rows）
Expected entity to have a primary key (in entity:"e.S.V") 把聚合视图（group by 或没保留主键的 select）暴露成 OData 实体 聚合结果没有唯一键，cds2edm 无法生成 EntityType/Key 二选一：① 视图保留 key ID（示范项目的 OrderItemView 就是带主键的展开视图，可以暴露）；② 聚合结果改用服务层函数返回（示范项目的 getOrderTotal / getOrderSummary） npx cds compile srv/book-order-service.cds --to edmx 无 [ERROR]；curl …/$metadata 里能看到 <Function Name="getOrderSummary"> 且没有多余实体集（实体集数量 5）
Add “@cds.redirection.target” to either “BookOrderService.BookOrderItems” or “BookOrderService.OrderItemView” to select the entity as redirection target for “sap.training.bookorder.BookOrderItems” in this service; can't auto-redirect “BookOrderService.BookOrders:items” otherwise 同一个源实体（db.BookOrderItems）在一个服务里被投影两次（明细实体 + 展开视图），而父实体的 items 是导航属性 CAP 不知道 $expand=items 该跳到哪个候选实体，需要人指定唯一目标 在你想作为导航目标的那张投影上写一行注解（示范项目给的是明细实体）：@cds.redirection.target entity BookOrderItems as projection on db.BookOrderItems; 重新编译后 $metadata 里出现 <NavigationPropertyBinding Path="items" Target="BookOrderItems"/>；curl "…/BookOrders?$expand=items" 返回数组而不是报错

  4. 验证：页面能列出 BO-1001…，点进 Object Page 能看到明细表；Console 里没有红色错误。再用一条 curl 复核同一 URL，界面与命令的结果必须一致 —— 不一致说明你看到的是缓存（Cmd+Shift+R 硬刷新）。

7. 万能排错流程（5 步，任何报错都照这个走）

前面六节是「答案表」，本节是「检索与记录方法」。顺序不能换：跳过第 1 步直接猜原因，是最慢的路。

  1. 看现象：把原文一字不差抄下来。不转述、不概括。记录四样东西：原始报错文本、发生时的命令、文件:行:列（若有）、HTTP 状态码与响应体（若有）。
    为什么必要：整句搜索几乎搜不到（消息里混了你的项目名/路径），关键词搜索才准；而且「原文」本身就是分层的线索。
  2. 定位层：用第 0 节的漏斗把问题关进一层。判据：有 行:列 → 编译期（第 2 节）；> init from … 之后失败 → 播种期（第 2 节）；有 HTTP 状态码 → 运行时（第 3、4 节）；白屏/控制台 → 浏览器（第 5 节）；cf 输出 → 云端（第 6 节）。
    为什么必要：改错层的代价是「改完发现没变」，然后再改一层，最后不知道是哪次改动生效了。
  3. 最小复现：把项目缩到能重跑的最小范围。用 curl 直接打服务（绕开 Fiori）；用单张表/单个 CSV 复现 deploy 问题；用一个 handler 复现事件问题。
    为什么必要：能重复出现的 bug 才可修；不能复现的「修好了」是运气。
  4. 看日志与网络（同时看两侧）：服务端看 cds watch 终端（[odata] - … 与 [error] - …）或 cf logs <app> --recent；客户端看 DevTools → Network（状态码、响应体、请求 URL）与 Console。
