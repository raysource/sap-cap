0. 本页用法

这一页不是讲义，而是讲义的答案与评分手册。三种用法：课前准备、课中提问、课后验收。

课前准备（提前 1 天）

  • 把 第 1 节课表按你自己的时段改一遍（时刻是相对值），打印每人一份。
  • 跑一次环境自检：node -v、npx cds -v、npm run deploy、curl -u alice:alice "$SVC/$metadata" 四条全绿。
  • 读一遍 采分点与 卡点表，把你认为最可能发生的 5 条标出来，课上重点盯。
  • 给学员发学员版（记入表）与 课表；提醒他们提前做完 ① BTP 注册（注册是最容易被邮箱策略卡住的一步）。
  • 备好离线兜底：本课程可在无 BTP 账号时完成 ④–⑨（SQLite + mocked 认证），示范项目就是按这个前提设计的。

课中提问（每段结束前 10 分钟）

  • 从 第 3 节必问问题里按板块挑 2–3 题口头快问，学员答不出来就当场演示一遍，不算分。
  • 「必须掌握」的能力用采分点的「可观察的证据」当验收动作：让他做给你看，而不是让他复述。
  • 出现卡点先查 第 5 节：现象 → 他大概会怎么做错 → 你怎么引导（一句话解释）。
  • 每段末用该页的「本节测试」做 2 分钟闭卷小测，答案在 第 4 节。

课后验收（当天结束 / 一周后）

  • 按 第 7 节评分标准算分：自测 40 + 任务完成度 40 + 演示与答辩 20。
  • 三条硬门禁任何一个不过就是不合格：模型编译无 [ERROR]、npm test 全绿、bash test/odata-verify.sh 的 FAIL 0。
  • 要求学员交「证据」而不是「结论」：命令 + 输出 + db.sqlite 里的行数。判据见采分点的第三列。
  • 对不及格者：先补 卡点表里他踩过的那几条，再重跑 演示脚本 B（用它证明他真的会看日志定位）。
一句话记住本页的三条主线
  • 采分点看证据：能不能「做出来 + 说出为什么」；只会背概念不给分。
  • 必问问题看追问：第一问答对不算过，追问答得上才算他真懂。
  • 演示看定位：故意制造一个 409，看他能不能在 30 秒内指到 handler 的行号。

1. 课堂节奏表：11 个板块排成 2 天（20 小时）

下面这张表把 11 个板块排成 2 天 × 10 小时 = 1200 分钟的课堂节奏（学习路线里的 1260 分钟含自学部分，多出的 60 分钟留给课后练习）。 时段是相对时刻（00:00 指当天开课），请按你的作息平移。每段的四列就是讲师的动作清单：讲什么 / 演示什么 / 学员做什么 / 采分点。

课前必做：30 分钟环境检查（放在第一天 00:00–00:30）

这一段不讲新内容，只做一件事：把每个人卡在环境外的问题都暴露出来。三件事，逐人过。

  1. 核对版本与目标（5 分）：node -v → 期望 v20.x 或 v22.x（LTS）；npx cds -v → @sap/cds-dk 为 9.x；有 BTP 账号的人再跑 cf --version 与 cf target（期望看到正确的 org 与 space）。
  2. 把示范项目跑起来（15 分）：npm install → npm run deploy → npm start → 另一个终端 bash test/odata-verify.sh，期望 PASS 26 / FAIL 0。这一步同时验证了 Node ABI、SQLite、依赖安装与认证策略四件事。
  3. 登记卡点（10 分）：把每人的失败现象抄到白板上，对照 第 5 节卡点表现场解决；解决不了的让本人换用「离线路径」（不走 BTP，全部在林本地 SQLite 完成）。

采分点：能独立说出「我的 Node 版本 / 我的数据库 kind / 我的服务 URL」三个值，并能用一条 curl 证明服务在跑（curl -u alice:alice -o /dev/null -w '%{http_code}\n' "$SVC/\$metadata" → 200）。 不给分：能跑通 npm start 但说不出服务挂载在哪个路径、或把「匿名 401」当成故障。

3-1 概念（concept）

问题期望答案要点追问
用一句话说明 CAP 是什么，它用一套模型自动得到哪三样东西？ 「用一套模型描述领域与服务，自动得到 OData V4 API、数据库 schema、Fiori 可用的界面契约」。你要写的是模型、业务规则、授权规则与界面注解。 这三样里哪一样仍然必须由人写代码？→ 业务规则（handler）、授权规则（@restrict / 角色集合）、界面微调；声明是模型的事，判断是你的代码的事。
按顺序说出一次 GET 请求经过的阶段，401 与 403 分别在哪一步产生？ 解析（OData → CQN）→ 认证（401）→ 授权（403）→ before → on（缺省实现＝查数据库）→ after → 响应。 为什么 401 的响应体是裸文本而 403 是 OData 错误对象？→ 401 由认证中间件返回（尚未进入 OData 适配器的错误格式化），403 由 CAP 授权框架按 OData 错误规范返回；前端做错误提示时要区别对待。
本地 SQLite 上跑通，就等于能上 HANA 吗？ 不等于。差异在类型映射（String 无长度：SQLite NVARCHAR(255) vs HANA NVARCHAR(5000)；时间列 TIMESTAMP_TEXT vs TIMESTAMP）、DDL 方言、HDI 部署与 schema 演进、排序与大小写规则。 那你要怎么做才算「准备上云」？→ 用 --dialect hana（或 --to hdbtable）核对 DDL + 做一次真实部署 + 在路由上跑冒烟（$metadata 200 与一条业务查询）。

为什么必须用 Node 的 LTS 版本（20/22），不能用最新的非 LTS？ CAP 9 推荐 20/22 LTS；本地 SQLite 走 @cap-js/sqlite，其背后是原生模块 better-sqlite3，它按 Node 的 ABI（NODE_MODULE_VERSION）发布预编译包。非 LTS 的新版本可能还没有对应 ABI 的预编译包，安装或运行时报 ABI / NODE_MODULE_VERSION 不匹配。本站必须用 Node 22 才能装上（实测 v22.23.2）。 机器上装不了怎么办？→ 用 npx 临时取一个 22：export PATH="$(dirname "$(npx -y node@22 -p process.execPath)"):$PATH"，然后 node -v 确认；另一种做法是装 nvm 并用 nvm use 22。

3-4 CDS 建模（cds）

问题期望答案要点追问
订单与明细之间为什么不用 Composition，而用显式 Association？ 三条基于实测的理由：① 语义——本站明细行要能单独 POST / PATCH / DELETE、生命周期与订单头相对独立，不需要「父删子必删」，也不需要 Deep Insert / Update；② 物理上两者等价——Composition of many Items on items.order = $self 与 Association to many Items on … 编译出的 DDL 逐字相同（diff 无输出），FK 列都在子表 order_ID；③ 可预期性——普通关联 + 显式 FK 列让 CSV 表头与查询条件都能写死。 什么场景该用 Composition？→ 强从属的文档结构（发票行、行程行），并且你想要 Deep Insert 与级联删除、服务里自动暴露。
注意：不要讲「Composition 会让父表多出 FK 列、导致 $expand 为空」——本站在同版本工具链上无法复现，cds.html §5 的纠偏框有完整说明（题库这一条的措辞与此不一致，见 8 疑难问答 Q1）。
为什么 getOrderSummary 这种聚合不能用实体暴露？正确做法是什么？ group by 的结果没有主键，而 OData 实体必须可寻址（能按 key 取单行）；暴露它会在编译时报 Expected entity to have a primary key。正确做法：在服务里声明无绑定 function（返回 Decimal 或结构体数组），handler 里用 CQN 聚合返回。 那什么视图可以暴露？→ 保留了 key 的视图（示例如 OrderItemView），通常再配 @readonly 让它只读。
不想让它进数据库？→ 加 @cds.persistence.skip（--to sql 里该视图消失）~
$expand=items 返回空数组意味着什么？ 意味着子表那一侧的外键列里没有值（或列名不是你想的那个）。三步排查：① cds compile … --to sql 看子表真实的 FK 列名（普通关联是 order_ID；匿名内联 Composition 是 up__ID）；② 直接查子表该列是否有值（select count(*) from 子表 where order_ID is null）；③ 用 join 计数确认父子能对上（本站初始数据明细 9 行、能 join 上订单的也是 9 行）。 为什么 deploy 还会打印「成功」？→ 外键在库里不一定有约束（SQLite 默认不强制 FK），且 CAP 不会替你校验 CSV 里的外键指向——本站实测 book_ID=9999 时 deploy 仍成功、只是 join 结果为 0，必须自己查「孤儿行」（left join … where b.ID is null）。
改了 db/schema.cds（加/改/删列）之后，为什么常要「删库重建」而不是只重跑 deploy？ 三个原因：① cds deploy 是增量行为——本站在 SQLite 上实测「加列会 ALTER 成功、数据保留」，但删列/改语义不会让旧列消失，模型与物理表就会 drift（cds.html 排错 14）；② SQLite 是动态类型，改类型不报错（实测 price 从 DECIMAL 变 INTEGER 照样通过，旧数据保留）→ 与模型不一致且不告警；③ 种子数据只在建库时装载，重跑 deploy 不会清掉你手工造/测试写坏的残留行（第二次跑验收脚本的 6 条 FAIL 就是这么来的）。所以本地正确动作是：rm -f db.sqlite db.sqlite-shm db.sqlite-wal && npm run deploy（等同 data.reset()）。 一定要连 -shm / -wal 一起删吗？→ 要。SQLite 的 WAL/SHM 是附属文件，只删主文件会留下不一致状态（课程据此强调「删文件重建」是最彻底的隔离）。
生产（HANA）也能删库重建吗？→ 不能。生产要走 HDI 的正式演进路径（部署工件 / 迁移文件）。~
orderNo 这种业务键为什么不加 DDL 的 UNIQUE，唯一性谁保证？ 实测 --to sql --dialect hana 里 orderNo NVARCHAR(16) NOT NULL 之后没有 UNIQUE；唯一性由服务层 before('CREATE', BookOrders) 检查，重复时 req.reject(409, '订单号 … 已存在')——好处是错误消息可控、可在同一处做编号生成。 代价是什么？→ 并发下存在双写窗口（应用层检查不是原子的）；~ 对一致性要求高的场景可考虑数据库约束或序列，但要接受错误消息不再是业务语言。
匿名内联 Composition（Composition of many { … }）会带来什么意外？ 编译器会在后台生成实体并加一条回链关联 up_，子表主键是复合键、FK 列名变成 up__ID（实测 up__ID NVARCHAR(36) NOT NULL）。CSV 表头必须写 up__ID，否则 deploy 失败。 推荐写法？→ 具名子实体 + 显式关联（本站做法），列名可预期。

问题期望答案要点追问
订单开了 @odata.draft.enabled 之后，before('CREATE', BookOrders) 的校验在哪个请求上执行？ 在激活草稿（draftActivate）时执行，不在 POST 建草稿时执行。完整 URL：POST /odata/v4/book-order/BookOrders(ID=<UUID>,IsActiveEntity=false)/BookOrderService.draftActivate（注意动作名带服务名前缀）。POST 只产生草稿：响应 IsActiveEntity=false、orderNo=null。 为什么测试里「POST 后订单号是 BO-1005」永远失败？→ 把两个 201 混为一谈；只能靠 IsActiveEntity 与 orderNo 是否已生成区分，真正建单要看激活响应。
绑定动作的 URL 有什么不同？→ 要带 IsActiveEntity=true：/BookOrders(ID=…,IsActiveEntity=true)/submitOrder，否则可能打到草稿行。
@cds.redirection.target 解决什么问题？不加会怎样？ 当同一个源实体在一个服务里被投影两次（本站：BookOrderItems 与 OrderItemView）时，BookOrders:items 的导航目标无法自动判定。报错原文就写着修法：Add “@cds.redirection.target” to either … ; can't auto-redirect。本站把它加在 BookOrderItems 上，声明它以导航目标为准。 不加是编译期还是运行期失败？→ --to edmx 编译期直接 [ERROR]，位置精确到行:列。
那用日志/退出码判断吗？→ 不要：本站实测编译打印 [ERROR] 但命令退出码可能仍是 0，门禁脚本必须 grep '[ERROR]' 再 exit 1。
同一个「汇总」需求，什么时候用 @readonly 实体、什么时候用 function？ 判断标准是结果能不能寻址：带主键、能按 key 取单行 → 用实体（常配 @readonly，如 OrderItemView）；sum / count / group by 的结果没有主键 → 用无绑定 function。 为什么用「两次查询 + Map 拼装」实现 getOrderSummary？→ 把聚合压在数据库侧（一次 groupBy），避免「先查订单再逐单查合计」的 N+1。
自定义动作 submitOrder 为什么必须用 on 注册，不能用 after？ 自定义 action/function 没有缺省实现；on 是「代替缺省实现」，所以它必须自己实现全部逻辑。after 是在实现之后跑，用 after 注册时请求先走空实现 → 动作不被调用（失败）。before 只能做校验，无法完成状态迁移。 动作名有什么坑？→ 不要叫 read / create / run 这类与基类方法冲突的名字，可能覆盖框架方法。
after('DELETE', BookOrderItems) 里为什么不能取 req.data.ID？替代方案？ DELETE 请求没有 body，被删除的行也不会返回键值，req.data 里拿不到可用键；要从 req.params 取（本站写法：req.data?.order_ID ?? req.params[req.params.length - 1]?.order_ID），或在 before('DELETE') 里先记下父键。 漏了会看到什么？→ 删除明细后父订单的 totalAmount 不更新（合计偏大），而且不报错——正是「测试能守住、肉眼守不住」的典型 bug。
业务校验失败应该返回 400 还是 500？客户端能看到什么？ 可判定的业务错误用 req.reject(400/404/409, '消息') → 客户端拿到对应状态码 + 可读消息（含 code 与 @Common.numericSeverity）；未捕获异常 → 500，且生产环境 5xx 响应体会被脱敏（只回 500 Internal Server Error），除非显式设置 err.$sanitize = false——所以排 500 必须看服务端日志。 req.reject 和 req.error 的差别？→ reject 会中止请求（内部 throw）；error 只记录错误并继续，适合一次性收集多条校验。
写出「查 status=OPEN 的订单、只要 ID / orderNo、按 orderNo 倒序、取前 3 条」的 CQN。 await SELECT.from(BookOrders).columns('ID','orderNo').where({ status: 'OPEN' }).orderBy('orderNo desc').limit(3)；生成 SQL 是参数化的（… WHERE status = ? ORDER BY orderNo DESC LIMIT ?），值不会被拼进 SQL 字符串。 查询某订单的明细合计，where 写哪个字段？→ 外键列 order_ID（不是 order）；写成 order 条件会静默失效、变成全表合计。

3-6 Java 服务实现（java）

问题期望答案要点追问
从 Node 版换到 Java 版，哪些东西不用改、哪些必须重写？ 不用改：db/*.cds 领域模型、srv/*.cds 服务定义与注解（含授权与 UI 注解）、db/data/*.csv 种子数据、对外的 API 契约。必须重写：事件处理器（handler）、构建与依赖（pom.xml / Maven）、测试代码与启动方式。 唯一的例外是 @path：Node 把 @path 当完整路径，而 CAP Java 会把 servlet 基路径 /odata/v4 加在前面——照抄 Node 的 '/odata/v4/book-order' 会变成 /odata/v4/odata/v4/book-order（实测 404）。Java 侧要写 @path: '/book-order' 才能对外 URL 一致。
Java 版为什么能直接用同一份 db/？→ cds-maven-plugin 在构建期调用 cds build --for java，生成 cds.gen.* 类型类与 edmx/、csn.json 等资源。
Java 里怎么拿到「绑定动作」那一行的主键？ 用 CqnAnalyzer 解析请求的 target（实测 demo-java 的 handler 构造里 analyzer = CqnAnalyzer.create(model)，动作处理器里用 analyzer.analyze(req) 取出 key）。 Node 里对应什么？→ req.params[req.params.length - 1].ID（绑定动作的键在 params 里）。
写一个 Java 事件处理器的关键注解是什么？它怎么和 Node 的写法对应？ 类上 @Component + @ServiceName(BookOrderService_.CDS_NAME)，方法上用 @Before / @After / @On（配 event = CqnService.EVENT_CREATE 与 entity = BookOrders_.CDS_NAME）。对应关系：this.before('CREATE', …) ↔ @Before(event = …, entity = …)。 为什么 Java 版启起来是 8080 而 Node 版是 4004？→ 分别是 Spring Boot 的默认端口与 CAP Node 运行时的默认端口；两边都能改。~
Result.first(Class) 与 Result.single(Class) 有什么区别？ first(X.class) 取第一行、没有行时返回 Optional.empty()（所以要先 .orElse(null) 或 .isPresent()，本机就踩过 Optional<Books> 不能赋给 Books）；single(X.class) 要求恰好一行，0 行或多行都会抛异常。 什么时候用哪个？→ 已知唯一（按主键查）用 single，语义即「断言唯一」；查询可能为空、想自己判空用 first。
这不就是 Node 的 SELECT.one 吗？→ 思路一样，但 SELECT.one 在多于一行时行为不可依赖，所以两边都要保证 where 唯一。
Java 端点 404 时第一个该打开的页面是什么？为什么？ CAP Index Page（http://localhost:8080/）：它列出所有已注册服务的真实 URL——本机就是靠它发现路径被拼成 /odata/v4/odata/v4/book-order 的。 Java 侧 @path 与 Node 侧有什么不同？→ 见上一题：Java 的 @path 是相对基路径的，写 '/book-order'。
mvn compile 生成的 cds.gen 有价值吗？→ 有：类型安全的实体接口与动作上下文（BookOrdersSubmitOrderContext 等），字段/实体名写错会在编译期报错；没有它（全靠字符串）也能跑，但失去这层保护。

3-7 测试体系（testing）

问题期望答案要点追问
四层测试分别抓什么？各举一个「上一层抓不到」的例子。 第 0 层模型/语法检查（cds compile）：抓语法、未解析关联、缺主键、重定向歧义——例如少了 @cds.redirection.target 直接报 ERROR。
第 1 层 cds.test：进程内起服务做细粒度断言——例如「数量 0 → 400 且消息为『数量必须大于 0』」。
第 2 层 odata-verify.sh：从外部打 HTTP 的集成验收——例如草稿激活重复订单号 → 409、用错方法 → 405（第 1 层在进程内不易覆盖这些真实往返）。
第 3 层 UI 测试（Fiori 层）~：第 0/1 层都抓不到界面行为（列没显示、按钮不可用）。		 第 0 层抓不到什么？→ handler 里的逻辑错误（例如金额算错、req.data 取不到值）。
为什么同一份验收脚本第二次运行会出现 6 条 FAIL？ 因为脚本本身写数据，第二次运行时前置条件已变：明细行数 9 → 10、getOrderSummary() 4 → 5 行、BO-1001 已 SUBMITTED（再提交得 409 而非 200）、自动编号 BO-1005 → BO-1006、父订单合计 12000 → 20400 等。修法：跑前 rm -f db.sqlite* && npm run deploy（或在测试里 data.reset()）。 这 6 条 FAIL 说明测试有问题吗？→ 不，说明断言绑定了明确的前置条件，这正是有效测试；关键是把它显式化（重置库）而不是放宽断言。
数据库隔离有哪三种做法，代价分别是什么？ ① 重置现有文件（npm run deploy / data.reset()）：零配置、与手工验证一致；代价：会清掉手工数据，不能与服务同时写。
② 删除文件重建（rm -f db.sqlite db.sqlite-shm db.sqlite-wal && npm run deploy）：最干净、顺带验证「从零建库」；代价：慢，且必须连 WAL/SHM 一起删。
③ 独立测试库 / 内存库（credentials.url 指向 db-test.sqlite，或用 cds.test 的 in-memory 模式）：开发数据不受影响、内存库最快；代价：多一份配置，内存库跑完即消失不利排查。		 本站为什么必须在 before() 里 data.reset()？→ 项目把 requires.db.credentials.url 指向 db.sqlite，cds.test 连的就是这个文件，不重置就会污染开发数据。
为什么 CI 里不能用 cds watch，替代方案是什么？ cds watch 是常驻监视进程、不会退出（CI 会挂到超时），热重载在 CI 里也没有价值。替代：cds compile（或 cds build）做静态/构建检查 + npm start（cds-serve）起稳定服务跑集成测试。 服务就绪怎么等？→ 轮询健康检查（curl $metadata 返回 200 即继续，设次数上限），不要 sleep。

3-8 认证与授权（security）

问题期望答案要点追问
401 与 403 的差别是什么？各自怎么确认原因？ 401＝未认证，由认证层返回（凭据不存在/不成立），响应体是裸文本 Unauthorized（带 WWW-Authenticate）；403＝已认证但无权限，由 CAP 的授权框架按 @requires / @restrict 返回，响应体是 OData 错误对象（{"error":{"message":"Forbidden","code":"403"}}）。确认原因：401 查 cds env get requires.auth.kind 与凭据是否随请求发出；403 查注解里的角色名与 JWT 的 scope 是否对得上。 本站实测的两个样本？→ 匿名 GET /BookOrders → 401 纯文本；-u bob:bob（认证成立但无角色）→ 403 OData 错误体；-u alice:alice → 200。
mocked 与 dummy 的差别是什么？测匿名 401 该用哪个？ dummy 什么都不验证：实现就是 req.user = cds.User.privileged; next()，每个请求都当特权用户，所以匿名也 200——它是「关掉权限」的排障开关，绝不能用来测 401。mocked 是「假的登录」：走 Basic Auth，预定义若干用户（alice/bob/…）并默认带 "*": true 兜底，匿名请求会被 @requires 拦成 401（实测带 WWW-Authenticate: Basic realm="Users"）。测匿名必须用 mocked（或 basic / jwt）。 为什么 mocked 下 -u 任意用户名:任意密码 也 200？→ 内置 users 配置里 "*": true 放行未配置的用户名，且默认用户没配 password 时密码不校验。要收紧：显式写 "*": false 并给每个用户配 password。
那生产能用 mocked / dummy 吗？→ 不能；生产用 xsuaa（或 jwt），并在 [production] 档里显式固定。
CDS 里写 to: 'submit'，而 xs-security.json 里的 scope 是 $XSAPPNAME.submit——为什么这样才是对的？ 因为 CAP 比对时会把 JWT 中 scope 的 <xsappname>. 前缀剥掉再匹配：JWT 里是 demo-node-trial-dev.submit，对应 CAP 角色名就是 submit，所以 to: 'submit' 正确。三个名字必须分清：scope 名（$XSAPPNAME.submit）、CAP 角色名（submit，写在 to: 上）、role-template 名（OrderAdmin，只是打包单位，不能写进 to:）。 写错（比如 to: 'sub' 或写 role-template 名）会怎样？→ 本地 mocked 下常看不出问题，部署后必然 403；这就是最常见的「用户已分配角色集合但调用接口 403」的原因。
为什么 @readonly 不能表达「只有管理员能读」？ @readonly / @insertonly / @Capabilities 属于静态访问控制：它由运行时强制执行，但与用户无关（等价于 @restrict: [{ grant: 'READ' }]，默认 to: 'any'）。按角色控制要写 @restrict（或 @requires），例如 @restrict: [{ grant: 'READ', to: 'BookOrder.View' }]。 @requires: 'Viewer' 等价于哪条 @restrict？→ @restrict: [{ grant: '*', to: 'Viewer' }]。
实体上写了两段 annotate … with @(restrict: […]) 会怎样？ 编译时只有一行 WARNING：Duplicate assignment with "@restrict", using last，运行时后者整体覆盖前者——前一段里声明的权限会静默消失（实测 --to xsuaa 的输出里只剩后一段的角色 scope）。对策：把 @restrict 合并到一处。 怎么发现这种问题？→ cds compile srv --to xsuaa 看生成的 scopes 是否符合预期 + 把三态断言写进验收脚本。

3-9 Fiori UI（fiori）

问题期望答案要点追问
「界面由注解生成」的边界在哪里？改界面应该改哪里？ UI.* 注解决定列、筛选、标题、动作、Facets，编译进 $metadata 的 Annotations 段，由 Fiori Elements 渲染；但应用外壳仍然是前端工程的事——manifest.json（用哪个模板、路由怎么走）、Component.js、index.html。所以「加一列」改 CDS，「换模板/改路由」改 manifest.json。 怎么证明注解真的进了元数据？→ curl -u alice:alice "…/$metadata" | grep -c Annotation（本站实测 166）~。
本地打开 Fiori 应用显示 No data / 空白，按什么顺序定位？ ① 先看浏览器网络面板：$metadata 或实体请求是不是 401（本地没有 approuter / XSUAA 做登录跳转，页面不会带 Basic 凭据）→ 用 test/dev-proxy.js 注入 mock 认证；② 是不是 404 / URI 不匹配（manifest.json 的 dataSources.mainService.uri 要与服务 @path 一致）；③ 服务返回 200 但界面空 → 注解没进 metadata（grep Annotation）或 UI.LineItem 没配。 那个代理能带到生产吗？→ 不能。真实部署由 approuter + XSUAA 负责认证（xs-app.json 的 authenticationType: xsuaa + destination 的 forwardAuthToken）。

3-10 构建与部署（deploy）

问题期望答案要点追问
部署链路里每一步的产物是什么？ ① npx cds build --production → gen/srv（服务实现 + gen/srv/srv/csn.json、OData EDMX 等运行时资源）与 gen/db（HANA 工件：.hdbtable / .hdbview / .hdbtabledata）；② mbt build -t mta_archives → .mtar（含各模块的内容 + mta.yaml 声明的资源需求）；③ cf deploy …mtar -f → 创建/更新应用（…-srv、…-approuter）与服务实例（XSUAA、HDI 容器），并由 hdb 模块里的 HDI deployer 在 HANA 上建表并装载 CSV；④ 验证 → cf apps（都 started）+ 路由上 curl $metadata 返回 200（证明服务可达、认证通过、模型能序列化）。 谁真正在云端建表？→ 不是 cds build（它只生成工件），而是部署时 gen/db 模块里的 @sap/hdi-deploy；这也是为什么每次部署都会比对工件。
快速迭代时想跳过整体部署怎么办？→ cds deploy --to hana（只把 DB 工件推上去，服务仍本地跑）~。
「部署成功但没有表」的根因？→ 归档里没有 gen/db（常因为 production profile 没解析出 db.kind = hana），db-deployer 模块「成功」却什么都没建；验证两条命令：find gen -maxdepth 2 -type d（必须同时有 gen/db 与 gen/srv）与 cf logs demo-node-db-deployer --recent。
cds build 是谁在执行？→ mbt build 会先跑 mta.yaml 里 build-parameters.before-all 的 npm ci + npx cds build --production，所以「忘记先 build」不会出错，但改了模型没重新打包会部署出旧产物。
mta.yaml 里 hdb 模块与 hdi-container 资源是什么关系？ resources 里声明一个 com.sap.xs.hdi-container（service: hana、service-plan: hdi-shared），然后由服务模块与 hdb 模块引用同一个资源名——这样运行时应用与建表部署器连的是同一个 HDI 容器。 忘了绑定会怎样？→ 应用起得来但查不到表 / 连接失败；症状与「表名写错」很像，先看 cf services 与应用的绑定（cf env）。
部署到路由之后 401 或 404，最该查什么？ ① 401：认证链路——xs-security.json 是否随 MTA 部署（role-templates / scopes）、用户是否被分配角色集合、approuter 是否把 token 转发给后端（xs-app.json 的 authenticationType: xsuaa 与 destination 的 forwardAuthToken: true）。② 404：路由与服务路径——@path、approuter 的 xs-app.json 目标、后端应用是否 started。 用 cf logs <app> --recent 能看到什么？→ 请求日志与错误栈（注意部署后 5xx 的响应体是脱敏的，只能从日志看原因）。
为什么讲课要强调「本地 26 条断言全绿」而不是「我本地能跑」？ 断言把「能跑」变成可复核的证据：PASS 26 / FAIL 0 里包含匿名 401、草稿激活 409/400、状态迁移 409、只读实体 405、聚合函数 404 等负向场景；同一套脚本可以指向云端地址（BASE=）做部署后验收，是本地与云端之间唯一的共同判据。 哪三条是硬门禁？→ 模型编译无 [ERROR]、npm test 全绿、bash test/odata-verify.sh 的 FAIL 0。

概念 · 本节测试（8 题）

  1. CAP 是什么 + 自动产生的三样东西？→ 用一套模型描述领域与服务，自动得到 OData V4 API（含 OpenAPI）、数据库 schema、Fiori 可用的界面契约。
  2. 三层对应文件与依赖方向？→ 模型 db/schema.cds、服务 srv/*.cds + .js、UI app/*/annotations.cds + webapp/；依赖单向：UI → 服务 → 模型（改模型影响面最大：数据库、API、界面同时变）。
  3. --to sql / --to edmx / --to csn 各给谁？→ sql 给数据库（建表与演进）；edmx 给 OData 客户端与 Fiori（$metadata）；csn 是编译器与运行时之间的规范化中间表示（运行时读 CSN，不读 .cds 文本）。
  4. GET 请求的阶段与 401 / 403 的位置？→ 解析（OData → CQN）→ 认证（401）→ 授权（403）→ before → on（缺省实现＝查库）→ after → 响应。
  5. 聚合为什么不能用实体暴露？正确做法？→ 无主键 → 不可寻址；用服务里的无绑定 function 返回聚合结果（本站 getOrderTotal / getOrderSummary）。
  6. Node 与 Java 共享什么、不共享什么，真实工作量在哪？→ 共享领域模型、服务定义与注解（含授权与 UI）、CSV 种子数据、API 契约；不共享 handler 代码、构建与测试脚手架；工作量在重写 handler + 工程结构 + 测试。
  7. 把「授权对象 + AUTHORITY-CHECK」和「@restrict + 角色集合」对上 → 两者都是「对象 + 权限 + 检查」：ABAP 的检查写在应用代码里显式调用（ABAP 层）；CAP 的 @restrict 由框架在授权阶段强制执行（你不写检查代码，只写规则）；角色集合对应给用户打包授权。~
  8. 从 12 个误解里挑两个并纠正 → 评分点：能说出「为什么会误解 + 正确理解 + 怎么验证」。常见答案：CDS 不是数据库（它是编译器，产物才是 DDL）；@readonly 不是权限（它是与用户无关的静态约束）；注解不是注释（是可执行元数据）；本地 SQLite 通过 ≠ 云端通过。

⑤ Node 服务 · 本节测试（7 题）

  1. @path 不写会怎样？为什么仍建议显式写？→ CAP 会按服务名推导 URL（BookOrderService → /odata/v4/book-order）；显式写死的好处是以后改服务名 URL 不变，前端与测试脚本不用跟着改。
  2. 为什么 BookOrderItems 那行必须加 @cds.redirection.target？不加的报错关键词？→ 因为服务里有两个实体源自 db.BookOrderItems（BookOrderItems 与 OrderItemView），BookOrders:items 无法自动重定向；报错关键词 can't auto-redirect（原文还写着 Add "@cds.redirection.target" to either …）。
  3. 什么时候用 @readonly 实体、什么时候用 function？→ 判断标准：结果能不能按主键寻址。带主键的视图 → 实体（+ @readonly）；sum / count / group by 无主键 → 无绑定 function。
  4. 草稿下 before('CREATE') 在哪个请求执行？完整 URL？→ 在 draftActivate 请求上：POST /odata/v4/book-order/BookOrders(ID=<UUID>,IsActiveEntity=false)/BookOrderService.draftActivate。
  5. after('DELETE', BookOrderItems) 为什么不能取 req.data.ID？替代方案？→ DELETE 没有 body、被删行不返回键值；用 req.params（本站兜底写法），或在 before('DELETE') 里先记下父键。
  6. 业务校验失败返回 400 还是 500？客户端各自看到什么？→ 用 req.reject(400, …)：客户端看到 400 + 可读消息（含 code 与 @Common.numericSeverity）；未捕获异常 → 500，且生产环境的 5xx 响应体被脱敏，只有服务端日志能看到原因。
  7. CQN fluent API（status=OPEN、只取 ID/orderNo、orderNo 倒序、前 3 条）？→ SELECT.from(BookOrders).columns('ID','orderNo').where({ status: 'OPEN' }).orderBy('orderNo desc').limit(3)。

⑦ 测试体系 · 本节测试（7 题）

  1. 四层各抓什么？各给一个「上一层抓不到」的例子。→ 见 3-7 第 1 题。例子：第 0 层抓不到 handler 逻辑错误（金额算错）；第 2 层能抓「方法用错 → 405」「草稿激活 → 409」这类真实 HTTP 语义，而第 1 层在进程内不易覆盖。

  3. 写一条负向断言（数量 0 → 400 且消息为「数量必须大于 0」）→ cds.test 风格：const err = await POST(`/odata/v4/book-order/BookOrderItems`, { order_ID: ID, book_ID: 1001, quantity: 0 }).catch(e => e)，然后 expect(err.response.status).to.equal(400)、expect(err.response.data.error.message).to.equal('数量必须大于 0')；chk 风格：chk 'POST 数量 0 → 400' 400 -X POST "$SVC/BookOrderItems" -d '{"order_ID":"…","book_ID":1001,"quantity":0}'（再断言消息）。
  4. 为什么第二次运行出现 6 条 FAIL？对应什么数据变化、怎么修？→ 脚本自己写数据：明细 9→10、getOrderSummary() 4→5、父订单合计 12000→20400、BO-1001 已 SUBMITTED（重复提交 409）、自动编号 BO-1005→BO-1006、OrderItemView 行数与首行订单号变化；修法：跑前 rm -f db.sqlite* && npm run deploy（或 data.reset()）。
  5. 三种数据库隔离做法与代价？→ 见 3-7 第 3 题（重置现有文件 / 删除文件重建 / 独立测试库或内存库）。
  6. CI 里为什么不能用 cds watch？替代它的两条命令？→ 常驻不退、CI 会挂到超时，热重载无用；替代：cds compile（静态检查）与 npm start（cds-serve 起稳定服务）。
  7. DoD 里哪几条是硬门禁？→ 模型编译无 [ERROR]、npm test 全绿、bash test/odata-verify.sh 的 FAIL 0（FAIL>0 即非 0 退出）——标准是「可自动判定、结果二元、阻断合并」。

⑧ 权限 · 本节测试（8 题）

  1. 401 与 403 分别由链路上哪一环产生？怎么确认原因？→ 401 认证层（未认证，裸文本 + WWW-Authenticate）；403 CAP 授权框架（已认证但角色/条件不足，OData 错误体）。确认：cds env get requires.auth.kind 与凭据、注解里的角色名 / JWT 的 scope。
  2. 为什么测匿名 401 不能用 kind: dummy？用它测出来是什么？→ dummy 直接把每个请求设成特权用户（req.user = cds.User.privileged），匿名也返回 200，永远测不出 401；测匿名要用 mocked（或 basic / jwt）。
  3. mocked 下 -u anyname:whatever 也 200 的原因？要只认自己配的用户怎么做？→ 内置 mock 用户配置里有 "*": true 兜底放行未配置用户名，且默认用户没配 password 时密码不校验；收紧：显式写 "*": false 并给每个用户配 password。
  4. to: 'sub'（少一个字母）而 xs-security.json 里是 $XSAPPNAME.submit 会发生什么？为什么？→ 编译/本地常常看不出问题，部署后调用必然 403：CAP 把 JWT scope 去掉 <xsappname>. 前缀后得到 submit，与 to: 'sub' 不匹配。
  5. 服务级 @requires 与实体级 @restrict 同时存在时的判断规则？→ 两者都要满足：请求先过服务级要求（authenticated-user 是伪角色、由运行时自动附加），再过实体级的 grant / to / where 判定；任一层不满足即拒绝（403）。
  6. 同一实体两段 annotate … with @(restrict: […])，最终生效哪一段？编译时提示？→ 后者整体覆盖前者；编译只有一行 WARNING Duplicate assignment with "@restrict", using last，前一段的权限静默消失（--to xsuaa 输出里能看出只剩后一段的 scope）。
  7. @readonly 是「只读」还是「权限控制」？要「只有管理员能读」怎么写？→ 它是与用户无关的静态访问控制（等价 @restrict: [{ grant: 'READ' }]，默认 to: 'any'）；按角色控制写 @restrict: [{ grant: 'READ', to: 'BookOrder.View' }]（to 里是 CAP 角色名）。
  8. 角色集合、角色模板、scope、CAP 角色名的关系（画箭头链）？→ xs-security.json 的 scopes（$XSAPPNAME.submit）→ role-templates（OrderAdmin，scope-references 指向该 scope）→ 管理员在 cockpit 组装 role-collection 并分配给用户 → XSUAA 签发 JWT，把 scope 写进 scope 声明 → CAP 的 jwt 认证剥掉 <xsappname>. 前缀 → 得到 CAP 角色名 submit → 与 CDS 里 to: 'submit' 比对。

⑥ Java 服务 · 本节测试（8 题）

  1. Java 版与 Node 版共享哪些文件？哪些必须各写一份？→ 共享 db/*.cds（领域模型）、srv/*.cds（服务定义与注解，含 @path 之外的授权与 UI 注解）、db/data/*.csv；各写一份：pom.xml（父 POM + srv 模块）、Java 事件处理器、JUnit 测试、Application 启动类。
  2. @Before / @After / @On 对应 Node 的什么？→ this.before(event, Entity, cb) / this.after(...) / this.on(...)；Java 用注解声明（@ServiceName 指定服务、event / entity 指定目标），写错实体名在编译或启动期报错，而 Node 写错是运行时静默不触发。
  3. 绑定动作的键为什么必须用 CqnAnalyzer 取？→ 键不在请求体里，而在请求的目标（CQN）上；Java 侧请求本身就是 CQN，需要用 CqnAnalyzer 从 target 解析出实体键（Node 侧对应 req.params[req.params.length-1].ID）。
  4. Result.first(Class) 与 Result.single(Class) 的区别？→ first 返回 Optional（无行即空，需 orElse(null) / isPresent()）；single 要求恰好一行，0 行或多行都抛异常。
  5. 为什么 CAP Java 里 @path 不能照抄 Node 的写法？→ Node 把 @path 当完整路径，CAP Java 会再加一次 servlet 基路径 /odata/v4，于是变成 /odata/v4/odata/v4/book-order（实测 404）；Java 侧写 @path: '/book-order'。
  6. 端点 404 时第一个该打开的页面？为什么？→ http://localhost:8080/（CAP Index Page）：它列出所有服务的真实 URL，本机就是靠它发现路径被拼了两遍。
  7. mvn compile 生成的 cds.gen 有什么价值？没有它可行吗？→ 价值是类型安全：实体接口（getOrderNo() 等）、动作上下文（BookOrdersSubmitOrderContext）、常量（BookOrders_.CDS_NAME），字段/实体名写错编译期就报错；不用它也能跑（全靠字符串），但失去这层保护。
  8. §10 里那条 401 说明了什么？要修的话第一步做什么？→ 说明「$metadata 能打开 ≠ 数据能读」：本地 mock 用户没生效时，匿名与具名请求都被拒（所以「匿名 401」这条断言没有区分度）。第一步：按 CAP Java 官方文档核对当前版本（4.9.1）的 mock 用户属性名与层级并打开配置诊断日志；或者直接建真实 XSUAA + cds bind 走真实认证。注意 cds.requires.auth.kind: dummy 是 Node 侧写法，Java 侧不适用。

⑨ Fiori UI · 本节测试（15 题）

  1. 「列表 → 详情」之外举两个必须 freestyle 的场景并说明原因 → 向导/多步表单（一个页面改多个实体集的复杂编排）、自定义可视化（甘特图 / 地图 / 拖拽看板，超出 FE 的 Chart / DataPoint）、批量编辑 + 即时计算、与第三方 UI 库或非 OData 接口深度混用、非业务形态页面（大屏）。原因：Fiori Elements 是「标准业务形态」的模板，硬拗要用大量扩展点；折中方案是「FE 为主 + 少量自定义扩展」。

  6. 列表的「创建」按钮要在注解里声明吗？→ 不需要：草稿注解 @odata.draft.enabled 自动带来 Create/Edit/Save/取消。

⑩ 部署 · 本节测试（15 题）

  1. 为什么 cds build --production 有时只生成 gen/srv？怎么确认？→ 因为 production profile 里没有解析出 db.kind = hana（例如只写了 "[production]": { "auth": "xsuaa" }），构建就只产出 nodejs 那部分；确认：find gen -maxdepth 2 -type d（有没有 gen/db）、cds env get requires.db --profile production、ls gen/db/src/gen（有没有 *.hdbtable）。
  2. 「部署成功但没有表」的根因在哪一层？两条自验证命令？→ 在归档/构建层：gen/db 缺失 → db-deployer 模块没有制品，「成功」却什么都没建。两条命令：find gen -maxdepth 2 -type d 与 cf logs demo-node-db-deployer --recent。
  3. build-parameters.before-all 的作用？删掉会怎样？→ 它在打包前执行命令（本站是 npm ci + npx cds build --production）；删掉后不会自动构建，模块拿到的 gen/ 是旧产物或不存在 → 部署出旧版本、或应用缺依赖起不来。
  4. provides: srv-api 与 requires: - name: srv-api / group: destinations 的关系？为什么不硬写后端 URL？→ provides 把本模块 URL 暴露为提供物（srv-url: ${default-url}），approuter 用 requires + group: destinations 通过 ~{srv-url} 引用它；不硬写是因为每次部署路由域名都可能变。
  5. forwardAuthToken: true 的作用？去掉后会怎样？→ 让 approuter 把用户 token 转发给后端 destination；去掉后后端收不到 Authorization，通过 approuter 访问会 401（直连 srv 带 token 仍 200）。
  6. HDI 容器为什么必须用 hdi-shared？换 schema 会怎样？→ hdi-shared 提供受 HDI 托管的容器与部署语义（工件比对、技术用户、由 deployer 建表并装载 CSV）；schema 是裸 schema，没有部署器能力 → 表建不出来（部署「成功」但库里没有表）。
  7. xs-security.json 是手写的吗？改了权限注解之后要做什么？→ 不是：由 CDS 注解生成（cds compile srv --to xsuaa / cds add xsuaa --for production）。改了权限注解要重新生成并重新构建部署（scope 变了，角色集合里的引用也要跟着更新）。
  8. mbt build -t mta_archives 里 -t 的含义？.mtar 默认文件名规则？→ -t 是输出目录；默认文件名是 <MTA ID>_<version>.mtar（本站 demo-node_1.0.0.mtar）。
  9. 用 Operation ID 取部署日志的完整命令？日志怎么看？→ cf dmol -i <operation ID> -d mta-logs；不知道 ID 时 cf mta-ops 或 cf dmol --mta demo-node --last 3 -d mta-logs。日志按模块拆分，先看失败的那个模块（srv / db-deployer / approuter），Process finished. 才是整体成功。
  10. 回滚 MTA 的正确做法？为什么说没有一键回滚？数据库要不要一起回滚？→ 保留每个版本的 .mtar，回滚时按旧版本号重新打包并重新部署（必要时 --version-rule ALL）；因为 MTA 部署是声明式同步（把云端对齐到归档）而不是保存快照。数据库要单独考虑：HDI 默认「只增不删」（undeploy.json 不含 hdbtable），回滚应用通常能成功，回滚表结构要自己写迁移——所以 schema 变更要向后兼容（先加列、双写、再切换、最后清理）。
  11. 为什么 --sso 不能用在 CI？替代方案与权限注意？→ 它需要浏览器交互（打印一次性验证码后打开浏览器），CI runner 没有浏览器；--sso-passcode 的一次性码也无法自动续期。替代：流水线里用专用技术用户的凭据（例如 cap-js/cf-setup 之类的 action 自动登录），权限给最小集（Space Developer），并定期轮换凭据。
  12. CI 里 test -d gen/srv / test -d gen/db 在拦什么？→ 拦「构建产物缺失」：缺 gen/db 就会变成「部署成功但没有表」（最常见的生产事故形态），缺 gen/srv 会部署出空应用；把存在性写进门禁能提前在流水线 fail。
  13. 清理环境时为什么「先解绑再删服务实例」？--delete-services 的代价？→ 绑着应用的服务实例删不掉，所以要先 cf unbind-service；cf undeploy … --delete-services 会连服务实例一起删，数据库内容随之消失（确认后再加）。
  14. 同一份归档部署到 dev / prod，推荐用什么机制区分差异？→ 用 MTA 扩展描述符（-e prod.mtaext / dev.mtaext）覆盖实例数、内存、计划等差异，mta.yaml 只保留一份（cds up --overlay 也支持）。

8. 疑难问答：学员最容易追问的「为什么不…」（12 条）

学员的追问正确回答（可直接照着讲）常见误解回答（要当场纠偏）
「为什么不干脆用 Composition？它看起来更『正式』」 因为本站的明细行是独立可寻址的业务对象（要能单独 POST / PATCH / DELETE），也不需要「父删子必删」和 Deep Insert；而且两种写法编译出的 DDL 逐字相同，Composition 的差异在运行时语义（Deep Insert / Update、级联删除、服务自动暴露）。详见 cds.html §5。 「因为 Composition 会让父表多出 FK 列，CSV 填不到。」——本站在同一版本工具链上 diff 不出这个现象，cds.html §5 的纠偏框有实测；题库 node.json 第 16 题沿用了这个旧说法，教学请以 cds.html 为准。
「为什么聚合不能直接暴露成实体？加个 key 不就行了？」 OData 实体必须可寻址（能按 key 取单行）。sum / count / group by 的结果里没有能唯一标识一行的键，随便加个 key 也只是「不报错」，语义上仍然没有单行标识。正确做法是无绑定 function。 「加 @readonly 就能暴露。」——@readonly 管的是「能不能写」，不管「有没有主键」。
「为什么改了模型要删库重建？框架不能自动迁移吗？」 本地开发用的 cds deploy 是增量行为：加列会 ALTER 成功、旧数据保留；删列/改语义不会让旧列消失；SQLite 是动态类型，改类型根本不报错（实测 DECIMAL → INTEGER 照样通过）——不删库你无法确认「手里这个库就是模型描述的那个库」。删库重建还顺带验证「从零建库」这条路径（CI 就是这么跑的）。 「生产也这么干。」——不行。生产要走 HDI 的正式演进路径（部署工件 / 迁移），删库等于丢数据。~
「为什么非要 Node LTS？我装最新版不行吗？」 因为 @cap-js/sqlite 依赖原生模块 better-sqlite3，原生模块按 Node 的 ABI（NODE_MODULE_VERSION）发布预编译包。非 LTS 的新版本常常还没有对应 ABI 的包，安装或运行就会失败；CAP 9 的推荐是 20/22 LTS。 「LTS」= 长期支持，是「稳定」而不是「更旧」；本课程用 22 LTS（不是 21）。
「为什么不能在 handler 里自己 cds.tx() 开事务？显式一点不是更好吗？」 CAP 的承诺是「事件处理器里你已经在事务中」：一个请求 = 一个根事务，before / 实现 / after 共享它，成功一起提交、抛错一起回滚。在 handler 里再开事务属于误用，在 SQLite 上还可能导致死锁。cds.tx() 只用于非请求上下文（脚本、定时任务），cds.spawn() 用于当前事务之外的后台任务。 「不用事务就没有一致性。」——一致性的来源是「请求事务 + 回写失败会抛出 → 一起回滚」，本站的汇总回写正是靠这一点。
「为什么 @readonly 不算权限？我明明挡住了写操作。」 因为它是静态访问控制：对所有用户一视同仁（等价 @restrict: [{ grant: 'READ' }]，默认 to: 'any'），与「谁」无关。要按角色控制必须写 @restrict（grant / to / where）或服务级 @requires。 「加了 @readonly 就等于只有管理员能读。」——它连「谁能读」都没表达。
「为什么负向测试不能只断言状态码？400 对不就说明拦住了吗？」 状态码只能证明「被拒绝了」，不能证明「按预期的原因拒绝」。库里有多条校验时，任何一条触发都会是 400；只有断言业务消息（例如「数量必须大于 0」）才能证明你测的是目标规则。 「消息会变，断言消息太脆。」——消息是你的业务契约的一部分，改消息本来就该同步改测试。
「为什么生产不能用 mocked？本地用得挺顺。」 因为 mocked 不校验真实身份（内置用户 + "*": true 兜底、默认不校验密码），dummy 更是直接把每个请求当特权用户。正确做法是在 package.json 的 [production] 档显式把 auth.kind 设为 xsuaa（或 jwt），并确保没有 mocked / dummy 流进生产。 「生产用 mocked 一样安全。」——它连「你是谁」都不知道，授权注解全是空转。
「为什么 orderNo 不加数据库 UNIQUE？不会重复吗？」 本站刻意把唯一性交给服务层（before('CREATE') 查重 → req.reject(409, …)），这样错误消息是业务语言、编号生成与查重在同一处；实测 DDL 里确实没有 UNIQUE。 「服务层检查等于数据库保证。」——不是原子的，并发下有窗口；~ 强一致场景应加数据库约束或序列，并接受错误消息不再可读。
「为什么 .cdsrc-private.json 里看不到密码？云端不用密码怎么连？」 它只存绑定元数据（平台 / org / space / 实例名 / 服务键名），凭据在运行时才由框架去 CF 解析。这样文件可以安全地留在本地而不进 Git，也不会随代码泄露。 「把同事的文件拷过来就能用。」——既不安全，也常因环境不同（org/space/实例）而失败；正确做法是自己 cds bind。
「为什么一定要写 @cds.redirection.target？编译器猜不出来吗？」 因为服务里有两张实体都源自同一张源实体（BookOrderItems 与 OrderItemView），BookOrders:items 指向谁在语义上不唯一，编译器必须由你指定，报错原文里就给了修法。 「随便挑一张应该也行。」——选错会让 $metadata 里的导航绑定指向另一张实体，前端能显示但关联字段可能不对。
「为什么服务里建议显式写 @path？让框架推导不是更省事？」 框架推导的 URL 会随服务名变化（BookOrderService → /odata/v4/book-order）。显式写死以后，改服务名不会悄悄改掉 URL，前端 manifest.json 与测试脚本都不用跟着改。 「@path 决定数据库文件路径。」——它只管服务在 URL 上的前缀。
