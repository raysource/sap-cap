本页的诚实声明 本机的 Java 侧验证做到了：编译成功、服务启动成功、模型注册成功、CSV 灌入 H2 成功、$metadata 返回 200； 但带认证的实体读取没有验证通过——CAP Java 的本地 mock 用户配置在本会话中没找出正确写法（§10 有完整记录与排查方向）。 因此本页凡标注「✅ 实测」的都是本机真实输出，标注「⚠ 未验证」的请当作待验证的手顺， 不要当成已经跑通的事实。Node 版（⑤）的全部结论都是实测通过的。

0. 为什么要学第二个运行时

CAP 的核心主张是模型与运行时解耦：领域模型（db/schema.cds）与服务定义（srv/*.cds） 是同一份文件，换的只是实现运行时。本站示范项目就是证据：project-code/demo-node/db/ 与 project-code/demo-java/db/ 的 schema.cds 内容一致，srv/book-order-service.cds 也只差一行（见 §8 的 @path 坑）。

你的背景先看哪个为什么
JavaScript / TypeScript⑤ Node 服务 → 本页Node 版上手快、改一次 .cds 就能看到结果；本页用于理解「同一模型换运行时」的成本在哪
ABAP / Java 企业后端本页 → ⑤Java 版有编译期类型检查与 Spring 生态，适合大团队；Node 版用于快速验证模型
架构决策本页 §6 对照表两种运行时的取舍（类型安全 / 启动速度 / 依赖体积 / 生态 / 团队技能）

两个容易踩的结构问题
  • db/ 在项目根，不在 srv/ 里 —— cds-maven-plugin 在 srv 模块里执行， 但会向上找到含 package.json 的项目根，因此日志里会看到 Filling sap.training.bookorder.Books from ../db/data/…。

3. pom.xml 与编译链

根 POM 只做三件事：锁版本、声明模块、配置编译器与 enforcer。真正的“CAP 味道”在 srv/pom.xml 的 cds-maven-plugin —— 它把 CDS 编译、Node 下载、npm 安装、H2 schema 生成、Java 类型生成串成一条链：

xml
<plugin>
  <groupId>com.sap.cds</groupId>
  <artifactId>cds-maven-plugin</artifactId>
  <executions>
    <!-- ① 清掉上次生成物 -->
    <execution><id>cds.clean</id><goals><goal>clean</goal></goals></execution>
    <!-- ② 按需下载一个 Node 到插件缓存（本机已有 Node 时也照跑，保证可复现） -->
    <execution><id>cds.install-node</id><goals><goal>install-node</goal></goals></execution>
    <!-- ③ npm ci（装 @sap/cds-dk） -->
    <execution><id>cds.npm-ci</id><goals><goal>npm</goal></goals>
      <configuration><arguments>ci</arguments></configuration></execution>
    <!-- ④ 解析依赖（含 @sap/cds/common 等复用包） -->
    <execution><id>cds.resolve</id><goals><goal>resolve</goal></goals></execution>
    <!-- ⑤ 编译模型：cds build --for java，并生成 H2 建表脚本 -->
    <execution><id>cds.build</id><goals><goal>cds</goal></goals>
      <configuration><commands>
        <command>build --for java</command>
        <command>deploy --to h2 --with-mocks --dry --out "${project.basedir}/src/main/resources/schema-h2.sql"</command>
      </commands></configuration></execution>
    <!-- ⑥ 从模型生成 Java 接口（cds.gen.*） -->
    <execution><id>cds.generate</id><goals><goal>generate</goal></goals>
      <configuration>
        <basePackage>cds.gen</basePackage>
        <betterNames>true</betterNames>          <!-- orderNo() 而不是 orderNo() 这种更好用的名字 -->
        <cqnServiceGetters>true</cqnServiceGetters>
        <linkedInterfaces>true</linkedInterfaces>
      </configuration></execution>
  </executions>
</plugin>

4. 生成的类型：cds.gen 里有什么

模型编译后，每个实体/服务/动作/函数都会生成 Java 接口。写处理器就是对着这些类型写，所以先把它们的命名规则记住：

生成的类对应模型里的什么你在处理器里怎么用
cds.gen.bookorderservice.BookOrderService_服务 BookOrderService@ServiceName(BookOrderService_.CDS_NAME)
…bookorderservice.BookOrders / BookOrderItems / Books / Customers服务投影后的实体before 钩子的参数类型；item.setAmount(...) 这类 setter
…bookorderservice.BookOrders_实体的静态访问器（字段 path）BookOrders_.CDS_NAME、o.orderNo().eq("BO-1001") 的类型化条件
…bookorderservice.BookOrdersSubmitOrderContext绑定动作 submitOrder@On(event="submitOrder", entity=BookOrders_.CDS_NAME)，参数用这个类型
…bookorderservice.GetOrderTotalContext / GetOrderSummaryContext两个无绑定函数取参数 ctx.getOrderNo()；回结果 ctx.setResult(...)
…bookorderservice.OrderSummaryRow服务里定义的 type OrderSummaryRowOrderSummaryRow.create() 然后 setter 逐个赋值
…bookorderservice.BookOrdersDraftActivateContext 等@odata.draft.enabled 带来的草稿事件需要干预草稿流程时才用（本示范未干预）

字段常量的命名是大写下划线（BookOrders.ORDER_NO、BookOrderItems.ORDER_ID）， 而访问器方法是驼峰（getOrderNo()、getOrderId()）。注意 customer : Association to Customers 的生成结果是 getCustomer()（对象）+ getCustomerId()（外键值），不是 getCustomer_ID() —— 写错会有 “找不到符号” 的编译错。

5. 事件处理器：与 Node 版一一对应

完整文件见 源码页（#f- 锚点）。下面是骨架与关键片段：

java
@Component
@ServiceName(BookOrderService_.CDS_NAME)
public class BookOrderServiceHandler implements EventHandler {

    private final PersistenceService db;      // 相当于 Node 里的 cds.db
    private final CqnAnalyzer analyzer;       // 取绑定动作的键

    public BookOrderServiceHandler(PersistenceService db, CdsModel model) {
        this.db = db;
        this.analyzer = CqnAnalyzer.create(model);
    }

    /* ① 编号生成 + 校验 + 派生字段（Node: this.before('CREATE', BookOrders, …)） */
    @Before(event = CqnService.EVENT_CREATE, entity = BookOrders_.CDS_NAME)
    public void beforeCreateOrder(BookOrders order) {
        if (order.getOrderNo() == null || order.getOrderNo().isBlank()) {
            order.setOrderNo(nextOrderNo());
        } else if (db.run(Select.from(BookOrders_.class)
                .where(o -> o.orderNo().eq(order.getOrderNo()))).first(BookOrders.class).isPresent()) {
            throw new ServiceException(ErrorStatuses.CONFLICT, "订单号 " + order.getOrderNo() + " 已存在");
        }
        if (order.getOrderDate() == null) order.setOrderDate(LocalDate.now());
        if (order.getStatus() == null)     order.setStatus("OPEN");
        order.setStatusCriticality(criticalityOf(order.getStatus()));
        Integer customerId = order.getCustomerId();
        if (customerId != null && db.run(Select.from(Customers_.class)
                .where(c -> c.ID().eq(customerId))).first(Customers.class).isEmpty()) {
            throw new ServiceException(ErrorStatuses.BAD_REQUEST, "顾客 " + customerId + " 不存在");
        }
    }

    /* ② 明细：金额 = 单价 × 数量 */
    @Before(event = { CqnService.EVENT_CREATE, CqnService.EVENT_UPDATE }, entity = BookOrderItems_.CDS_NAME)
    public void beforeBookOrderItems(BookOrderItems item) {
        Integer quantity = item.getQuantity();
        if (quantity != null && quantity <= 0) {
            throw new ServiceException(ErrorStatuses.BAD_REQUEST, "数量必须大于 0");
        }
        Books book = db.run(Select.from(Books_.class).where(b -> b.ID().eq(item.getBookId())))
                .first(Books.class).orElse(null);
        if (book == null) throw new ServiceException(ErrorStatuses.BAD_REQUEST, "图书不存在");
        item.setAmount(book.getPrice().multiply(BigDecimal.valueOf(quantity)));
    }

    /* ④ 绑定动作：键在 CQN 里，必须用 CqnAnalyzer 取（不要解析 URL） */
    @On(event = "submitOrder", entity = BookOrders_.CDS_NAME)
    public void submitOrder(BookOrdersSubmitOrderContext ctx) {
        Map<String, Object> keys = analyzer.analyze(ctx.getCqn()).rootKeys();
        String id = (String) keys.get(BookOrders.ID);
        …
        ctx.setResult(String.format("订单 %s 已提交，合计 %s JPY（%d 行）",
                order.getOrderNo(), order.getTotalAmount().toPlainString(), items.size()));
    }

    /* ⑤ 无绑定函数：聚合结果没有主键，不能做成实体 */
    @On(event = "getOrderTotal")
    public void getOrderTotal(GetOrderTotalContext ctx) {
        BookOrders order = db.run(Select.from(BookOrders_.class)
                .where(o -> o.orderNo().eq(ctx.getOrderNo()))).first(BookOrders.class).orElse(null);
        if (order == null) throw new ServiceException(ErrorStatuses.NOT_FOUND, "订单号不存在");
        ctx.setResult(totalOf(order.getId()));
    }
}
三个必须记住的类型细节
  • 事件常量来自 CqnService（不是 CdsService：CAP Java 4.9.1 里没有这个类）。
  • Result.first(Class) 返回 Optional<T>；需要对象就 .orElse(null)， 只想判断存在就用 .isPresent() / .isEmpty()。Result.single(Class) 才直接返回对象。
  • 绑定动作的键只能从 CQN 里取（CqnAnalyzer.analyze(ctx.getCqn()).rootKeys()），context 上没有 getID()。

6. 与 Node 版逐项对照

维度Node.js 版（⑤）Java 版（本页）实际影响
项目结构db/ srv/ app/ + package.json父 POM + srv 模块 + db/Java 多一层 Maven 模块，构建命令从 npm 换成 mvn
模型文件完全相同（只差 @path，见 §8）这是 CAP 最有价值的地方
处理器注册this.before('CREATE', Entity, cb) 运行时注册@Before(event=…, entity=…) 注解 + Spring BeanJava 写错实体名是编译或启动期报错，Node 是运行时静默不触发
类型安全无（req.data 是普通对象）生成的接口（getOrderNo() 等）Java 重命名字段时 IDE 能一次改完；Node 要靠测试兜底
查询写法CQN：SELECT.from(BookOrders).where({...})类型化 CQL：Select.from(BookOrders_.class).where(o -> o.orderNo().eq(x))都能下推到 SQL；Java 版写错列名编译不过
错误响应req.reject(400, msg)throw new ServiceException(ErrorStatuses.BAD_REQUEST, msg)都要用框架 API，抛裸异常会变成 500
事务请求事务（ambient CQN）PersistenceService 自动加入请求事务两边都不需要手写 begin/commit
本地数据库SQLite 文件（db.sqlite）H2 内存（schema-h2.sql）Java 每次启动都是干净数据；Node 要 rm db.sqlite 重建
启动npm start（cds-serve，4004 端口）mvn spring-boot:run（Tomcat，8080 端口）端口不同；Java 启动约 1.4 秒（本机实测）
测试mocha + cds.test / curl 脚本JUnit 5 + MockMvcJava 测试能直接 mvn test 进 CI
部署产物nodejs buildpack 推源码Maven 打 jar（*-exec.jar）+ JVM buildpack内存占用、启动时间、镜像体积都要按 Java 计
依赖体积~330 包 / 数十 MBMaven 依赖在本机 ~/.m2（首次拉取较慢）Java 首次构建慢、之后靠本地仓库
适合场景快速验证模型、小服务、全栈 JS 团队大团队、强类型、已有 Spring 生态与运维选型要看团队技能与既有资产，不是性能

8. 本机踩到的 4 个坑（每个都真实发生过）

#现象根因修复
1所有请求 404，错误来自 ResourceHttpRequestHandler（“No static resource odata/v4/…”）用 -pl srv / devtools 重启后 servlet 注册丢失从 srv 目录直接 mvn spring-boot:run，并关闭 devtools 自动重启
2404 依旧，但这次是 CAP 自己返回的@path 语义在两种运行时不同：Node 把 @path 当完整路径；CAP Java 会把 servlet 基路径 /odata/v4 加在前面 → 实际变成 /odata/v4/odata/v4/book-orderJava 版写 @path: '/book-order'，对外 URL 两边一致
3找不到符号: クラス CdsServiceCAP Java 4.x 的事件常量在 CqnService 上import com.sap.cds.services.cds.CqnService;
4Optional<Books> は Books に適合しませんResult.first(Class) 返回 Optional.first(X.class).orElse(null) 或 .isPresent()；需要单值可直接 .single(X.class)

9. 测试：JUnit + MockMvc

Java 侧的集成测试与 Node 的 odata-verify.sh 覆盖同一批规则： $metadata 公开、匿名 401、读 4 张订单、$expand 拿明细、两个函数、数量 ≤ 0 → 400、 派生金额与合计回写。写法（需要 spring-security-test 才能用 httpBasic(...)）：

java
@SpringBootTest
@AutoConfigureMockMvc
class BookOrderServiceTest {

    @Autowired MockMvc mvc;

    @Test void metadataIsPublic() throws Exception {
        mvc.perform(get("/odata/v4/book-order/$metadata")).andExpect(status().isOk());
    }

    @Test void anonymousIsRejected() throws Exception {
        mvc.perform(get("/odata/v4/book-order/BookOrders")).andExpect(status().isUnauthorized());
    }

    @Test void ordersAreReadable() throws Exception {
        mvc.perform(get("/odata/v4/book-order/BookOrders?$select=orderNo")
                .with(httpBasic("alice", "alice")))
           .andExpect(status().isOk())
           .andExpect(jsonPath("$.value.length()").value(4));
    }

    @Test void orderTotalFunction() throws Exception {
        mvc.perform(get("/odata/v4/book-order/getOrderTotal(orderNo='BO-1003')")
                .with(httpBasic("alice", "alice")))
           .andExpect(jsonPath("$.value").value(17400));
    }
}

{"error":{"code":"401003","message":"ログインする必要があります。"}}

# 而 $metadata 是 200、服务启动正常、CSV 也灌进去了 —— 只有「认证」这一步过不去。
# 启动日志里**没有** MockUsersSecurityConfig 那一行（这一点当时没注意，是关键线索）。

10.2 三种无效尝试（都是改错的地方）

尝试结果为什么无效
application.yaml 里写 cds.security.mock.enabled: true + users 列表形式仍然 401属性名本身没错，但认证中间件不在 classpath 上，这段配置没人读
用 SPRING_APPLICATION_JSON 注入同样的配置仍然 401同上：不是 YAML 绑定的问题
cds.requires.auth.kind: dummy仍然 401这是 Node 侧的写法；CAP Java 的本地认证走 Spring 的 mock 用户配置，不认这个属性

10.3 根因（官方文档一句话）

cap.cloud.sap → Security → Authentication 
text
CAP Java requires certain Maven dependencies to enable authentication middleware support.
Platform starter bundles cds-starter-cf and cds-starter-k8s ensure all required
dependencies out of the box.
即：cds init --java 生成的工程默认不带认证中间件的 starter，所以 mock 用户配置不会生效。 判断依据就是启动日志里没有 MockUsersSecurityConfig 那一行 —— 有它才说明 mock 认证真的启用了。

10.4 修复

xml
<!-- srv/pom.xml -->
<dependency>
  <groupId>com.sap.cds</groupId>
  <artifactId>cds-starter-cloudfoundry</artifactId>
</dependency>
yaml
# srv/src/main/resources/application.yaml —— 用「以用户名为键的 map」形式（官方示例 cloud-cap-samples-java 的写法）
cds:
  security:
    mock:
      users:
        alice:
          password: alice
          roles: [ admin ]
        bob:
          password: bob
          roles: []

由此得到两个可教学的运行时差异
  • $metadata 是否公开，两种运行时不同：Node 的 mocked 认证下匿名取 $metadata 是 200； Java 侧认证一旦生效，$metadata 也要凭据（匿名 401）。写测试断言必须按真实行为，不能照搬另一个运行时。
  • 只构建一个模块的坑：mvn -pl srv test 会触发 enforcer 的 ReactorModuleConvergence（"Module parents have been found which could not be found in the reactor"）， 必须从根目录 mvn test 或 mvn -pl srv -am test。
