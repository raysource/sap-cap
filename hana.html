2. 为什么需要数据库：CAP 的 db 层

cds.requires.dbdb/schema.cds · db/data/*.csv耗时 10 分

2-1 CAP 的 db 层是什么

CAP 把「数据模型」和「数据库」拆开了：db/schema.cds 只描述实体（领域模型），至于落到 SQLite 还是 HANA，由 cds.requires.db 的 kind 决定。这就是为什么同一份模型能本地跑、云端跑——切换的只是一行配置。

本地开发：sqlite 
json
"cds": {
  "requires": {
    "db": { "kind": "sqlite",
            "credentials": { "url": "db.sqlite" } },
    "auth": { "kind": "mocked" }
  }
}
生产：hana（由 cds add hana 写入） 
json
"cds": {
  "requires": {
    "db": {
      "[production]": { "kind": "hana" }
    }
  }
}
// 依赖里会多一条 @cap-js/hana

两条命令就能看清当前到底用哪个库（本教材项目实测）：default 是 kind: sqlite / impl: @cap-js/sqlite；加 --profile production 后变成 kind: hana / impl: @cap-js/hana。

2-2 SQLite 与 HANA Cloud 的差异（会影响写代码的六点）

维度本地 SQLite（@cap-js/sqlite）云端 HANA Cloud（@cap-js/hana）对你的影响
类型系统类型亲和性；CAP 生成 TIMESTAMP_TEXT / DATE_TEXT / NVARCHAR(n) / INTEGER / DECIMAL(13,2)（实测 DDL）强类型列存；生成 TIMESTAMP / DATE / NVARCHAR(n) / INTEGER / DECIMAL(13,2)日期时间列的名字不同（_TEXT 后缀），排查 DDL 时别慌
CDS 类型映射String(n) → NVARCHAR（默认长度 255，HANA 上默认 5000）；UUID → NVARCHAR(36)；Integer → INTEGER；Int64 → BIGINT；Decimal(p,s) → DECIMAL；Date → DATE；Boolean → BOOLEAN；LargeString → NCLOB；LargeBinary → BLOB同一份模型两种引擎都要能映射，所以尽量用 CDS 类型而不是数据库方言类型
标识符与大小写名字保留大小写，比较默认不区分 ASCII 大小写未加引号的标识符折叠为全大写；要区分大小写必须用双引号手写 SQL 时表名/列名一律按大写写（SAP_TRAINING_BOOKORDER_BOOKS）
表名生成sap_training_bookorder_Books（命名空间点换下划线，实体名保持）同一规则再加「未加引号 → 大写」：SAP_TRAINING_BOOKORDER_BOOKS看 SQL 报「表不存在」时，先按这条规则换算一次
JSON / 半结构化只能当文本存，没有原生 JSON 类型可以用 NCLOB 存 JSON，HANA 另有 JSON 文档存储等能力需要 JSON 检索/索引时，先把数据模型设计成 HANA 优先
视图与性能普通视图；单写入者，适合本地开发普通视图 + 计算视图（calculation view）；内存列存、多用户并发聚合类需求在 HANA 上可用计算视图；但要记住 CAP 的 OData 实体仍需主键
自系统确认方法 类型映射与表名规则都以你本机的真实产物为准，两条命令即可复核：
① npx cds compile db/schema.cds srv/book-order-service.cds --to sql → 看 CAP 认为的列类型（本地通用 SQL）；
② npx cds build --for hana && cat gen/db/src/gen/*.hdbtable → 看真正送到 HANA 的 DDL 与列名（本页第 6 节的表名就是从第 ② 步实测得来的）。
带 ~ 的名称表示随发布可能变化。

3. 创建 SAP HANA Cloud 实例（数据库本体）

SAP HANA Cloud Centralcf create-service hana-cloud hana耗时 15–30 分（含启动）

3-1 前置：配额、订阅与角色

  1. 确认 entitlements：cockpit → Subaccount → Entitlements，搜索 SAP HANA。免费层/试用常见组合是：服务 SAP HANA Cloud 的 tools (Application) 与 hana-free，服务 SAP HANA Schemas & HDI Containers 的 hdi-shared / schema / securestore。缺哪条就在 Edit > Add Service Plans 里补。
  2. 订阅管理工具：Subscriptions 标签里给 SAP HANA Cloud 的 tools 计划建订阅。它是「管理界面（SAP HANA Cloud Central / Database Explorer）」的门票，不是数据库计划。
  3. 确认角色：Security > Users 里给自己分配能管理 HANA Cloud 的角色集合（管理界面按订阅的计划与角色开放）。
  4. 验证：cockpit → Instances and Subscriptions > Subscriptions 里能看到 SAP HANA Cloud 的订阅；点它能打开 SAP HANA Cloud Central。
自系统确认方法 计划名随免费层/trial/付费而不同（常见写法：hana-free、hana、hana-cloud-connection、relational-data-lake；旧区域可能还能看到 hana-cloud-trial ~）。以 Entitlements 与 cf marketplace -e hana-cloud 的实际输出为准，不要照抄本文或旧博客。

3-2 cockpit 手顺：从订阅到 RUNNING

  1. 打开 SAP HANA Cloud Central：cockpit → Instances and Subscriptions > Subscriptions → 点 SAP HANA Cloud 订阅行。免费层会先问「手动配置 / 克隆」，选 Configure manually。
  2. Create Instance：右上角 Create Instance → Type 选 SAP HANA Database。（另一种类型是 SAP HANA Cloud, data lake。）
  3. 填实例名与管理员密码：实例名（例 demo-hana）+ 管理员账号（DBADMIN）与密码。密码要在自己的密码管理器里留档——后面 Database Explorer 直连要用。
  4. 大小与可用性：免费层/试用固定 16 GB 内存 · 1 vCPU · 80 GB 存储，不可改；付费环境这一步才可调。
  5. Connections（IP 允许列表）：决定谁能从外部连进来。默认常常是「拒绝除 SAP 平台外的地址」（~），此时用 DBeaver / 本机 Python 直连会被拒；CAP 部署到 CF 是 BTP 内部通信，不需要把开发机 IP 加白。要直连就选允许全部或逐个添加 IP。
  6. 高级设置：备份、数据湖等（免费层多数只读）。确认后创建，实例状态经历 Creating → RUNNING；首次启动通常要几分钟。
  7. （需要时）Instance Mapping：如果实例不是在 CF 环境里直接建的，要把它映射到 CF org：Cloud Central → 选实例 → Manage Configurations > Instance Mapping → Sign Into the Cloud Foundry Environment → Add Mapping 选 org → Review and Save。第 4 节建 HDI 容器时要靠这个映射。
  8. 验证：Cloud Central > Instances 里实例状态 = RUNNING；从行末的 ⋯ 菜单能打开 Open in SAP HANA Database Explorer；用 ⋯ > Copy Instance ID 拿到实例 ID（第 4 节参数要用）。

3-3 CLI 对照（同一条记录，两种建法）

数据库实例本体也能用 CF CLI 建，参数以 JSON 传入（memory 单位 GB、systempassword 是 DBADMIN 密码）：

bash
# 数据库实例本体（SAP HANA Cloud / 计划 hana）
cf create-service hana-cloud hana demo-hana \
  -c '{ "data": { "memory": 32, "systempassword": "<你的密码>" } }'

# 查看与排错
cf services                       # 看实例与 last operation
cf service demo-hana              # 看状态详情

# 免费层/试用实例每天会被自动停止，需要时这样启动（停止把 false 换成 true）
cf update-service demo-hana -c '{ "data": { "serviceStopped": false } }'

三个命令各自的「验证」：cf services 里对应实例的 last operation 变成 create succeeded；cf service demo-hana 显示 status: create succeeded；cf update-service … serviceStopped false 之后再查，实例状态回到 running / available。

常见错误（创建实例阶段）
  • Create Instance 是灰的：没有 tools 订阅或没有对应 entitlement/角色。
  • Service plan hana not found：cf marketplace -e hana-cloud 核对计划名；trial 与付费环境的计划名可能不同（如 hana-free）。
  • 创建卡在 Create in progress 很久：属正常（要分配资源并启动）；超过十几分钟仍在进行，用 cf service <实例名> 看最后一步。
  • HDI 容器建不起来，报「no database available」：实例没 RUNNING 或没做 Instance Mapping，回第 3-2 节第 7 步。

4. 创建 HDI 容器与计划取舍

SAP HANA Schemas & HDI Containerscf create-service hana hdi-shared耗时 10 分

4-1 先分清三条记录

记录服务名（CLI 里的 label）计划它是什么
SAP HANA Cloud 订阅—（Application 订阅，不是 CF 服务实例）tools管理界面的门票：SAP HANA Cloud Central / Database Explorer
数据库实例本体hana-cloudhana、hana-free（~ 随环境）、hana-cloud-connection真正的 SAP HANA 数据库，跑在 BTP 里，有 DBADMIN
HDI 容器（CAP 用这个）hana（显示名 SAP HANA Schemas & HDI Containers）hdi-shared / schema / securestore受 HDI 管控的 schema + 技术用户；表由部署流程创建

为什么 CAP 选 hdi-shared：HDI（HANA Deployment Infrastructure）把 schema 里的对象交给部署流程托管——每次部署比对设计时工件（.hdbtable / .hdbview / .hdbtabledata）与数据库现状，创建或更新对象，并用技术用户而不是 DBADMIN 连接。schema 计划只是给一个裸 schema（没有 HDI 部署能力），securestore 用于 Secure Store；tools 是管理界面订阅，与建表无关。

4-2 手顺（cockpit 与 CLI 二选一）

  1. cockpit 路：Instances and Subscriptions > Instances > Create → Service 选 SAP HANA Schemas & HDI Containers → Plan 选 hdi-shared → Instance Name 例 demo-hana-db → 下一步填参数：把容器指到具体数据库实例，并给一个建议 schema 名。 
    json
    // 参数（JSON）——database_id 来自 Cloud Central 的 ⋯ > Copy Instance ID
{
  "schema": "BOOKORDER",
  "database_id": "<你的 SAP HANA Cloud 实例 ID>"
}
  2. CLI 路（等价，适合脚本化）： 
    bash
    # 先确认本区域里的服务名与计划名
cf marketplace -e hana          # 应看到 hdi-shared / schema / securestore
cf marketplace -e hana-cloud    # 数据库实例本体的计划（如 hana / hana-free）

# 建 HDI 容器
cf create-service hana hdi-shared demo-hana-db \
  -c '{ "schema": "BOOKORDER" }'

# 验证
cf services                     # demo-hana-db 的 last operation = create succeeded
cf service demo-hana-db         # 看详情与 status
  3. 验证：cf services 里 demo-hana-db 的 last operation 为 create succeeded；cockpit 的 Instances and Subscriptions 里同名实例状态为 created；随后 cf create-service-key demo-hana-db demo-hana-db-key 能建出服务键（cds bind 也会自动建，见第 5 节）。
自系统确认方法 服务名（label）与计划名随区域与发布变化，且「显示名」与「CLI label」常常不同：显示名 SAP HANA Schemas & HDI Containers 在 CLI 里是 hana。判断方法只有一个：在目标子账户里执行 cf marketplace -e hana，把输出的 service 与 plans 两栏抄进命令。任何博客（含本文）给的组合都要用这条命令复核。
验收
  • Entitlements 里有 hdi-shared 配额，cf marketplace -e hana 能看到 hdi-shared。
  • demo-hana-db 实例状态 create succeeded。
  • 能说出「hdi-shared / schema / tools」三者的差别，以及为什么 CAP 必须用 hdi-shared。

5. 与 CAP 项目绑定

cds bindcds watch --profile hybrid.cdsrc-private.json · mta.yaml耗时 20 分

5-1 三种「绑定」不是一回事

方式凭据放在哪什么时候用
CF 服务绑定（部署时）BTP 注入到应用的 VCAP_SERVICES 环境变量部署到 Cloud Foundry 后，运行时由平台注入，代码里不写凭据
cds bind（本地 hybrid）只把「去哪取凭据」写进 .cdsrc-private.json，凭据在 cds watch 时动态解析，不落盘本地跑服务、连云端 HANA / XSUAA 做真实联调
cds bind --exec不写文件，把解析后的凭据通过 VCAP_SERVICES 环境变量注入子进程跑集成测试、CI 流水线，最干净的一种

5-2 手顺：从绑定到端到端验证

  1. 先准备项目：cds add hana（生产切 HANA）与 cds add mta（生成 mta.yaml）；只做本地 hybrid 联调时可以加 cds add hana --for hybrid，它会把 HANA 配置加到 [hybrid] profile 里。
  2. 登录 CF 并 target 到正确 org/space：cf login --sso 后 cf target 核对三行（API endpoint / org / space）。绑定用的就是当前 target。
  3. 绑定：cds bind db --to demo-hana-db。服务名 db 可以省略（db 是 hana kind 的默认服务名）；没有服务键时会自动创建 <实例>-key。 
    bash
    cf login --sso
cf target                                  # 验证 org / space 正确

cds bind db --to demo-hana-db
#   [bind] - Retrieving data from Cloud Foundry...
#   [bind] - Binding db to Cloud Foundry managed service demo-hana-db:demo-hana-db-key with kind hana.
#   [bind] - Saving bindings to .cdsrc-private.json in profile hybrid.
#   [bind] - TIP: Run with cloud bindings: cds watch --profile hybrid

cds bind --help            # 需要时查 -2 / --for / --exec / --on 的真实语义
#   -2 | --to <instance>[:<key>]   -4 | --for <profile>（默认 hybrid）
#   --exec  把凭据以 VCAP_SERVICES 注入被执行的命令
  4. 用 hybrid 启动本地服务：cds watch --profile hybrid。此时服务仍在本地跑，但 db 指向云端的 HDI 容器。
  5. 验证（两层都要看）：① cds env get requires.db --profile hybrid 输出里 kind 为 hana 且带 binding 信息；② 浏览器访问 /odata/v4/book-order/BookOrders，返回的是云端表里的真实数据（例：BO-1003 状态 SUBMITTED、totalAmount 17400）。
  6. 测试场景用 --exec：cds bind -2 demo-hana-db --profile integration-test --exec -- npm run integration-test，不产生任何凭据文件。

5-3 mta.yaml 里的资源定义（部署路径）

第 5-2 节走的是本地联调；真正部署时，绑定关系写在 mta.yaml 里。下面这份是本教材示范项目 cds add hana mta 之后真实生成的内容（节选）：

yaml
modules:
  - name: demo-node-srv            # 服务模块
    type: nodejs
    path: gen/srv
    requires:
      - name: demo-node-db          # 引用下面的资源
  - name: demo-node-db-deployer    # 建表模块（HDI deployer）
    type: hdb
    path: gen/db
    requires:
      - name: demo-node-db
resources:
  - name: demo-node-db
    type: com.sap.xs.hdi-container
    parameters:
      service: hana                 # CLI label：SAP HANA Sche
mas & HDI Containers
      service-plan: hdi-shared

两条要点：(1) 资源名（demo-node-db）是 MTA 内部的名字，部署时会创建/复用一个同名 CF 服务实例；也可以让 MTA 复用已有实例（把 parameters 里的 service/service-plan 去掉、改成显式指定现有实例名或加 config）。(2) 服务模块与建表模块引用的是同一个资源，所以服务拿到的连接信息和建表用的是同一个容器。

自系统确认方法 绑定与 hybrid 的细节以本机 CLI 为准：cds bind --help（看 -2/--to、-4/--for、--exec、-n/--on）、cds env get requires --profile hybrid（看解析后的配置）。.cdsrc-private.json 的字段结构随版本书可演进（本文写作时含 kind / binding{type,org,space,instance,key,vcap,resolved}）——以生成出来的文件内容为准，不要手写这个文件。
验收
  • .cdsrc-private.json 里只有 binding 元数据，没有任何密码（可打开文件确认，或用 grep -c password .cdsrc-private.json 检查为 0）。
  • cds env get requires.db --profile hybrid 显示 kind: hana。
  • cds watch --profile hybrid 下访问 /odata/v4/book-order/BookOrders 能返回数据。

6. 用 Database Explorer 看 CAP 生成的表

SAP HANA Database ExplorerCatalog · SQL Console耗时 15 分

6-1 进 Database Explorer 的两条路

  1. 路 A（推荐，先做完第 8 节的部署）：SAP HANA Cloud Central → Instances → 实例行末 ⋯ > Open in SAP HANA Database Explorer；或在 Database Explorer 里 Add 一个 HDI 容器连接。
  2. 路 B（在 BAS 里）：Full Stack Cloud Application 预置了 SAP HANA Database Explorer 扩展，它会以新标签打开 Database Explorer。这也是「为什么 CAP 的 dev space 要带这个扩展」的原因。
  3. 用 DBADMIN 直连（可选）：Database Explorer 里用管理员账号连数据库本体，能看到所有 schema；注意第 3 节设的 IP 允许列表要放行你的出口 IP。
  4. 验证：Database Explorer 左侧出现该 HDI 容器/schema 节点，展开 Catalog 能看到 Tables 与 Views 分组；右上角/顶部状态区显示连接名与数据库版本。

6-2 实体名 → 表名的映射规则（本页最重要的一条）

CAP 生成数据库对象名时用的是 plain names 规则：点（命名空间分隔符）换成下划线，再整体折叠为大写（未加引号的标识符在 HANA 里本来就是大写）。本教材项目实测结果：

CDS 里的实体本地 SQLite 表名（实测）HANA 里的表名（由 .hdbtable / .hdbtabledata 推出）
sap.training.bookorder.Bookssap_training_bookorder_BooksSAP_TRAINING_BOOKORDER_BOOKS
sap.training.bookorder.Customerssap_training_bookorder_CustomersSAP_TRAINING_BOOKORDER_CUSTOMERS
sap.training.bookorder.BookOrderssap_training_bookorder_BookOrdersSAP_TRAINING_BOOKORDER_BOOKORDERS span>
sap.training.bookorder.BookOrderItemssap_training_bookorder_BookOrderItemsSAP_TRAINING_BOOKORDER_BOOKORDERITEMS
sap.training.bookorder.OrderItemView（带主键的视图）视图，同名规则SAP_TRAINING_BOOKORDER_ORDERITEMVIEW

列名同样是「实体元素名照旧、大写折叠」，关联（Association）会额外生成外键列，命名规则是「导航属性名 + _ID」：BookOrders.customer → CUSTOMER_ID；BookOrderItems.order → ORDER_ID；BookOrderItems.book → BOOK_ID。这些名字在你手动 join 时全靠它对上。

自系统确认方法 不要凭记忆写表名——用项目自己的产物确认，一条命令即可：
bash
npx cds build --for hana
ls gen/db/src/gen/*.hdbtable          # 每个实体一个文件，文件名就是实体全名
head -1 gen/db/src/gen/*.hdbtable     # 看里面的 COLUMN TABLE <表名>

7. 可跑的 SQL（join 与聚合）

7-1 先确认 schema 与表清单

  1. 打开 SQL Console：Database Explorer 的 SQL Console（在 Cloud Central 的 Instances 页也能直接开；快捷键 Ctrl+Alt+C）。
  2. 切 schema：顶部中段显示当前 schema，点它可以下拉更换；也可以直接用 SQL： 
    sql
    -- 建议的 schema 名是建 HDI 容器时给的（本项目  BOOKORDER）
SET SCHEMA BOOKORDER;

-- 表清单与行数：确认 CAP 建了哪些表、各有多少行
SELECT TABLE_NAME, RECORD_COUNT
  FROM M_TABLES
 WHERE SCHEMA_NAME = CURRENT_SCHEMA
 ORDER BY TABLE_NAME;
  3. 验证：结果里能看到 4 张表（BOOKS / BOOKORDERS / BOOKORDERITEMS / CUSTOMERS）与视图；行数应与 db/data/*.csv 的行数一致——Books 5 行、Customers 3 行、BookOrders 4 行、BookOrderItems 9 行（本项目的 CSV 就是这些数字）。
为什么行数对不上？ 如果表在但行数是 0，说明表由部署建好、但初始数据没进来：检查 db/data/*.csv 文件名是否是 <命名空间>-<实体名>.csv，并确认构建产物里有对应的 .hdbtabledata（第 8 节）。

7-2 主表 + 明细表 + 客户表 join 与聚合

sql
-- 每张订单：客户名、明细行数、明细金额合计
SELECT O.ORDERNO                       AS ORDERNO,
       C.NAME                          AS CUSTOMER,
       O.STATUS                        AS STATUS,
       COUNT(I.ID)                     AS LINES,
       SUM(I.AMOUNT)                   AS ITEM_TOTAL
  FROM SAP_TRAINING_BOOKORDER_BOOKORDERS      AS O
  JOIN SAP_TRAINING_BOOKORDER_BOOKORDERITEMS  AS I ON I.ORDER_ID = O.ID
  JOIN SAP_TRAINING_BOOKORDER_CUSTOMERS       AS C ON C.ID = O.CUSTOMER_ID
 GROUP BY O.ORDERNO, C.NAME, O.STATUS
 ORDER BY O.ORDERNO;

-- 图书维度的销量：谁卖得最多（验证明细 → 图书 的外键 BOOK_ID）
SELECT B.ID                               AS BOOK_ID,
       B.TITLE                            AS TITLE,
       SUM(I.QUANTITY)                    AS SOLD_QTY,
       SUM(I.AMOUNT)                      AS SOLD_AMOUNT
  FROM SAP_TRAINING_BOOKORDER_BOOKORDERITEMS AS
 I
  JOIN SAP_TRAINING_BOOKORDER_BOOKS          AS B ON B.ID = I.BOOK_ID
 GROUP BY B.ID, B.TITLE
 ORDER BY SOLD_AMOUNT DESC;

-- 明细逐行明细（把 order 关联展开，看到 orderNo 与书名的连接关系）
SELECT O.ORDERNO, B.TITLE, I.QUANTITY, I.AMOUNT
  FROM SAP_TRAINING_BOOKORDER_BOOKORDERITEMS AS I
  JOIN SAP_TRAINING_BOOKORDER_BOOKORDERS     AS O ON O.ID = I.ORDER_ID
  JOIN SAP_TRAINING_BOOKORDER_BOOKS          AS B ON B.ID = I.BOOK_ID
 ORDER BY O.ORDERNO, I.ID;

第一条查询的预期结果（与 db/data/*.csv 一致，也用于和 OData 对账）：

ORDERNOCUSTOMERSTATUSLINESITEM_TOTAL
BO-1001北京华信书业OPEN316000.00
BO-1002北京华信书业OPEN13600.00
BO-1003上海博文出版中心SUBMITTED317400.00
BO-1004广州南方图书CLOSED27600.00
对账方法（这条比 SQL 本身更重要） 把 SQL 结果和 OData 端点比：
  • GET /odata/v4/book-order/BookOrders?$filter=status eq 'OPEN' → 2 条（BO-1001、BO-1002），与 SQL 的 STATUS 列一致。
  • GET /odata/v4/book-order/getOrderTotal(orderNo='BO-1003') → 17400，与 SQL 的 ITEM_TOTAL 一致。
  • 计算自检：BO-1001 = 2×4200 + 1×2800 + 1×4800 = 16000；BO-1003 = 4200 + 2×5200 + 2800 = 17400。
两边都一致，说明「服务层逻辑 + 数据库数据」都正确。本项目的 test/odata-verify.sh 里 25 项验证就是按这个思路做的（其中 1 项为已知的负向失败项，用于演示鉴权缺口）。

8. 建表与初始化数据的三条路径

cds deploy --to sqlitecds deploy --to hanagen/db耗时 15 分< /div>
路径谁执行建表在哪数据来源适用场景
cds deploy --to sqlite:db.sqlite本地 cds-dk本地 SQLite 文件db/data/*.csv 直接装载本地开发/教学；每次执行都是重建
部署时的 HDI deployer（mbt build + cf deploy）MTA 的 hdb 模块（gen/db）里的 @sap/hdi-deploy云端 HDI 容器的 schema构建时由 CSV 生成 .hdbtabledata正式部署（推荐）；后续每次部署都会比对工件
cds deploy --to hana本地 cds-dk 直接连 HANA（需要绑定/登录）云端 HDI 容器的 schema同上（构建出的工件）快速迭代数据库部分：只更新数据库，服务仍跑在本地

8-1 手顺：三种都跑一遍（看清差别）

  1. 本地路径（第 ② 页已用过）： 
    bash
    npm run deploy            # = cds deploy --to sqlite:db.sqlite
#   > init from db/data/sap.training.bookorder-Books.csv
#   > init from db/data/sap.training.bookorder-BookOrderItems.csv
#   successfully deployed to db.sqlite
  2. 云端路径（正式）：构建 → 打包 → 部署，其中 hdb 模块负责建表： 
    bash
    npx cds build --for hana      # 生成 gen/db 工件（.hdbtable / .hdbview / .hdbtabledata）
cat gen/db/package.json       # HDI deployer 的入口：@sap/hdi-deploy
#   "scripts": { "start": "node node_modules/@sap/hdi-deploy/deploy.js --use-hdb" }
mbt build -t gen --mtar mta.tar
cf deploy gen/mta.tar -f
  3. 云端路径（快速迭代）：只把数据库部分推上去，服务本地跑： 
    bash
    cf login --sso
cds bind db --to demo-hana-db          # 先绑定（第 5 节）

cds deploy --to hana                   # 内部会先执行 cds build
cds deploy --to hana --profile hybrid  # 按 profile 解析绑定信息
cds deploy --to hana --dry             # 只看 SQL，不执行（试探）
cds deploy --to hana --no-build        # 跳过 cds build（已构建过）
  4. 验证：三条路径跑完后，用第 7 节的 SQL 在 Database Explorer 里查行数——Books 5 行、Customers 3 行、BookOrders 4 行、BookOrderItems 9 行；若某张表 0 行，回到第 7-1 节的提示排查 CSV 命名与 .hdbtabledata。
HDI 的三个「反直觉」行为（务必记住）
  • HDI 默认不删除对象：你删掉一个实体或 CSV，数据库里的表和内容会继续留着。要真正删除需在 undeploy.json 里显式列出（cds add hana 会生成一份默认的）。永远不要把 .hdbtable 写进 undeploy——那等于删表丢数据。
  • CSV 数据归 HDI 所有：每次部署都会用 CSV 覆盖 .hdbtabledata 对应的数据。所以 CSV 只能放「配置类、用户不该改」的数据；需要用户能改的初始数据要用 include_filter 之类的机制区分。
  • schema 名不等于你给的名字：建容器时给的 schema 只是建议/前缀，实际 schema 可能有后缀。以绑定凭据里的 schema 字段为准。

12. 小结

这一页真正要记住的
  • 两条记录，别搞混：SAP HANA Cloud 的 hana / hana-free 是数据库本体；SAP HANA Schemas & HDI Containers 的 hdi-shared 才是 CAP 部署的目标。前者用 Cloud Central 管，后者用 cockpit 或 c f create-service 建。
  • 表名的规则只有一条：命名空间点换下划线 + 大写折叠。「表不存在」的九成原因是没按这条换算。
  • 本地与云端可以同时正确：cds bind（不落盘凭据）+ cds watch --profile hybrid 就地连云端库；先用 cds env get requires.db 确认，再谈功能。
  • 验证永远用两个维度：Database Explorer 里的 SQL（数据库视角）与 OData 端点（服务视角）互相对账。BO-1001 必须两边都是 16000。
  • 数据是可重建的：模型在 CDS、初始数据在 CSV、绑定在 mta.yaml——所以 Git 里必须齐；反过来说，CSV 不能放用户数据。
