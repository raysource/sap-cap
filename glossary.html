1-2 标注约定

怎么读「~」
  • 词条后带琥珀色「~」小标签（~）表示：说法本身有版本差异、或本站无法用官方文档逐字确认（例如某个 mta.yaml 字段的取值、某个缩写的旧称）。这类词条仍然给出了可自系统确认的方法，请在自己的环境里核对后再引用。
  • 不带 ~ 的定义，均可在 cap.cloud.sap（CAP 官方文档）或 help.sap.com（SAP 产品文档）里找到；带具体对象名的例子来自本课程示范项目 project-code/demo-node/（源码与实测输出，可用 ④ CDS 建模、⑤ Node 服务、⑦ 测试 里的命令复现）。
  • 术语的中文译法：课程用词优先，其次官方中文文档（例如 bound action 译「绑定动作」，Entitlement 译「权利」，实践中也常见「服务授权」的说法）。译名只是为了读起来顺，代码与界面里永远用英文标识符。
  • 本页不重复手顺与命令：要看「怎么做」请回到对应板块（BTP 注册见 ①，建模见 ④，授权见 ⑧）。

2. CAP 核心概念表

这一节是 CAP 自己的语言。第一列是中文名并带稳定锚点，最后一列一律给示范项目里的真实对象——认对象比背定义有用。

中文名英文（缩写展开）一句话定义示范项目里的例子
核心数据服务CDS — Core Data Services用声明式语言把「数据模型 + 服务」写成文本的这一层技术统称；CAP 的建模与暴露都建立在它上面。db/schema.cds、srv/book-order-service.cds、app/book-orders/annotations.cds 三种文件都是 CDS
「CSD」~CSD（不是 SAP 官方缩写）网络上确有人把 CDS 写成 «CSD»，SAP 官方没有这个缩写；本课程不使用，看到一律按 CDS 理解。—（本课程里出现的只有 CDS）
概念定义语言CDL — Conceptual Definition Language人写的 .cds 源文件语法：namespace / entity / type / aspect / association / service / annotation。entity BookOrders : managed { key ID : UUID; orderNo : String(16) not null; … }
模式表示CSN — Schema Notation（旧称 Core Schema Notation，读作 “season”）CDL 编译后的 JSON 中间模型，是所有下游产物（SQL / EDMX / OpenAPI）的共同输入。npx cds compile db/schema.cds --to csn 可直接看到 BookOrders.elements 被 aspect 摊平后的结果
查询语言CQL — Query Language（旧称 Core Query Language）类 SQL 的查询语言：既可以写视图主体，也可以用 fluent API 在 JS / Java 里构造查询。视图：OrderItemView as select from BookOrderItems；查询：SELECT.one.from(BookOrders).where({ orderNo })
查询表示CQN — Query Notation（旧称 Core Query Notation）CQL 解析后的纯对象表示（canonical plain object），运行时真正执行的东西；可用查询构造器、解析或手写得到。Node 里 SELECT.one.from(BookOrders).where(...) 产出的对象；Java 里 Select.from("bookshop.BookOrders") 同一回事
实体entity有主键的表或视图定义；投影到服务上就成为一个 OData 实体集。Books / Customers / BookOrders / BookOrderItems（4 个实体 + 1 个视图实体）
主键key唯一标识一行的元素。视图只有带主键才能作为 OData 实体暴露。key ID : UUID（示范项目的手写主键）；OrderItemView 保留 key ID 才能暴露
类型type可复用的元素或结构定义，不产生表；常用于动作/函数的返回结构。type OrderSummaryRow : { orderNo : String(16); customerName : String(80); … }
切面（复用片段）aspect可被实体 include 的字段集合；编译时展开进实体，所以一定会出现在 DDL 里（不是继承）。entity BookOrders : managed 展开出 createdAt/createdBy/modifiedAt/modifiedBy
托管字段managed（@sap/cds/common 的 aspect）自动补齐 4 个审计列（创建/修改的时间与用户），由框架在写入时填值。entity BookOrderItems : managed；SQLite 里对应 createdAt 等 4 列
规范通用 IDcuid — canonical universal ID（@sap/cds/common 的 aspect）只做一件事：给实体加 key ID : UUID（INSERT 时自动生成）。示范项目手写等价形式 key ID : UUID（见 ④ CDS 建模 的对照表）
本地化关键字localized（是关键字，不是注解）写在元素类型前，表示「该字段按语言存多份」；会额外生成 _texts 表与 localized_ 视图，读取要走视图。示范项目故意不用：Books.title 用普通 String(120)（原因见 ④ 第 4 节）
命名空间namespace模型文件顶部的前缀，决定完整限定名，也决定物理表名的前缀。namespace sap.training.bookorder; → 物理表 sap_training_bookorder_BookOrders
关联Association实体间的关系声明（含 to-one / to-many），查询时按需 join；不强制在父侧额外建列。customer : Association to Customers、items : Association to many BookOrderItems on items.order = $self
组合Composition「包含」关系：子对象生命周期依附父对象（父删子删），并在父表生成 FK 列；适合单据文档结构。示范项目刻意不用：改用普通 FK 列 + 显式 to-many 关联，这样 CSV 播种与 $expand 都正常
投影projection（as projection on）服务层对外暴露的视图（facade）：可以只挑部分元素、改别名、挂注解，是「API 面」的定义手段。entity BookOrders as projection on db.BookOrders actions { action submitOrder() returns String; }
视图view（as select from）定义在 db 层的只读查询对象，本身不存数据；带主键的视图可以当实体暴露。entity OrderItemView as select from BookOrderItems { key ID, order.orderNo as orderNo, … }
服务service服务定义：把实体与动作/函数组成一个 API，编译成 OData 端点与元数据。service BookOrderService @(requires: 'authenticated-user')，路径 /odata/v4/book-order
事件处理器event handler挂在某个事件上的函数/方法，用来扩展或覆盖框架的默认实现。Node：this.before('CREATE', BookOrders, async (req) => { … })；Java：@Before(event = "CREATE", entity = "BookOrders")
钩子三阶段hooks — on / before / afteron 取代默认实现，before 在 on 之前跑（校验），after 在 on 之后跑并拿到结果（回写、审计）。before CREATE 校验顾客；on submitOrder 状态迁移；after CREATE BookOrderItems 回写 totalAmount
注解annotation（@ 前缀）给模型或元素附加语义的声明，编译时进入元数据（EDMX），由框架或 UI 读取；本身不写业务逻辑。@odata.draft.enabled、@readonly、@cds.redirection.target、UI.LineItem
持久化persistence把模型落到数据库的那一层：生成表 / 视图 / 种子数据。可以用注解让它「不落地」或「只在运行时算」。npm run deploy（cds deploy --to sqlite:db.sqlite）建出 6 张表；@cds.persistence.skip 可跳过
草稿draft — @odata.draft.enabled编辑期先写草稿表，激活（draftActivate）后才写 active 表；Fiori 的 Create/Edit 流程全部建立在它上面。BookOrders 的草稿表 BookOrderService_BookOrders_drafts（连同 DRAFT_DraftAdministrativeData 是本站实测的建表结果）
实体数据模型 XMLEDMX — Entity Data Model XMLOData 元数据文档的外层 XML 格式，里面包着 CSDL（Common Schema Definition Language）；$metadata 返回的就是它。cds compile srv/book-order-service.cds --to edmx；部署后 curl …/$metadata 返回 200
开放数据协议 V4OData — Open Data Protocol，v4CAP 默认对外协议：REST 加一套标准查询选项与元数据描述，客户端可据此自动生成模型。服务挂在 /odata/v4/book-order；manifest.json 里 "odataVersion": "4.0"
元数据文档$metadata服务的自描述文档（EDMX），描述实体、动作、函数与全部注解；UI 与客户端据此工作。curl -u alice:alice …/$metadata 里含 BookOrderService；grep -c Annotation 实测 166 处
展开$expand一次请求把关联实体一起读出来（deep read），避免 N+1 次请求。GET /BookOrders?$expand=items&$select=orderNo,status,totalAmount 返回明细数组
常用查询选项$select / $filter / $orderby / $top / $skip / $countOData 标准查询选项：挑字段、过滤、排序、分页、取总数；CAP 会翻译成对应 SQL。?$filter=status eq 'OPEN' 实测返回 2 张订单；?$select=orderNo,status 只返回两列
动作action（有副作用，HTTP POST）表达「做一件事」的操作；声明在服务或实体上，返回类型可选。写状态、发消息、触发流程都用它。action submitOrder() returns String; 声明在 BookOrders 的 actions { … } 里
绑定动作bound action声明在实体内部的 action：URL 带实例键，天然绑定到「哪一张订单」，授权与语义都更精确。submitOrder；调用路径 POST /odata/v4/book-order/BookOrders(<ID>)/BookOrderService.submitOrder
无绑定动作unbound action声明在服务层的 action：没有实例上下文，参数自带全部信息。示范项目未使用（可写成 action doIt(param : String) returns String; 放在 service 里）
函数function（无副作用，HTTP GET）必须有返回值、不做状态变更；适合计算与聚合——聚合结果没有主键，不能当实体暴露，就用函数。function getOrderTotal(orderNo : String) returns Decimal(13,2);、function getOrderSummary() returns array of OrderSummaryRow;
严重度Criticality — UI.Criticality / CriticalityTypeUI 语义着色：0 Neutral（灰）／1 Negative（红）／2 Critical（黄）／3 Positive（绿）；值由服务端提供，客户端只读。派生字段 statusCriticality 由服务端维护，UI.LineItem 的 Criticality: statusCriticality 给状态列上色
重定向目标@cds.redirection.target当两张投影都源自同一个底层实体时，显式指定 $expand 该走哪一个。加在 entity BookOrderItems 上，否则编译报 can't auto-redirect BookOrders:items
只读@readonly写保护：任何用户都不能改。它不区分用户，所以不是授权。@readonly entity OrderItemView as projection on db.OrderItemView（实测对该实体 POST 返回 405）
入口检查@requires「访问这个资源需要什么角色」的简写，属于服务级/静态访问控制。service BookOrderService @(requires: 'authenticated-user') → 匿名请求实测返回 401
细粒度授权@restrict（grant / to / where）通用授权写法：对哪些事件、给哪些角色、满足什么实例条件；@requires: 'X' 等价于一条 grant: '*' 的 privilege。@restrict: [{ grant: ['READ','submit'], to: 'OrderAdmin' }]（详见 ⑧ 认证与授权）
服务路径@path指定服务对外的 URL 路径；不写则按服务名与协议默认值派生。@path: '/odata/v4/book-order'
种子数据seed data（db/data/*.csv）部署时导入的初始数据；CSV 表头必须与物理列名一致（含 FK 列，如 customer_ID），否则整次 deploy 失败。db/data/sap.training.bookorder-BookOrders.csv 等 4 个文件，实测导入 Books 5 / Customers 3 / BookOrders 4 / BookOrderItems 9 行
请求拒绝req.reject(status, message)（Node.js 事件上下文）主动以指定 4xx 状态码结束请求并带业务消息——业务错误一律 4xx，别让它变成 500。req.reject(409, '订单号 … 已存在')、req.reject(400, '数量必须大于 0')
事务transaction（Node：cds.tx / Java：Spring 事务 ~）一次请求一个事务；handler 里的读写默认在同一事务内，回滚即整批撤销。明细写入与父订单合计回写在同一次 POST 的事务里完成
类型生成器cds-typer（@cap-js/cds-typer）为 CDS 模型生成 TypeScript 类型声明，让 Node/TS 侧也能有代码补全与类型检查（可选工具）。示范项目用纯 JavaScript，未引入（引入后 handler 里的实体名会变成有类型的 API）
一句话记住 CAP 的语言层次 CDL（人写的）→ CSN（编译后的模型）→ CQL/CQN（查询的语言与对象）→ EDMX（对外说的元数据）→ OData V4（客户端真正调的协议）。 中间任何一环出问题，都在下一环表现：模型写错会在 CSN 里看出来，注解写错会在 EDMX 里消失，而客户端只会看到 400／404／500。

3. BTP 平台术语表

这一节是账号与平台层：谁付钱、谁有权、资源放在哪、应用怎么拿到凭据。第一列同样带稳定锚点。

中文名英文（缩写展开）一句话定义在本课程里的具体位置
全局账户Global Account你（或公司）与 SAP 之间合同的落地对象：用来管理子账户、成员、权利与配额；它与区域、运行环境无关。① BTP 注册 第一步注册出来的顶层账户，试用账号也是它
子账户Subaccount真正部署应用、使用服务、管理订阅的单元；彼此独立（安全、成员、数据都隔离），并且绑定到某一个区域。课程里建一个子账户 cap-training 用于本课程全部资源
目录Directory全局账户与子账户之间的层级容器：把子账户分组，并可以按目录分配权利与配额（也可用于管理员的角色集合）。单项目课程只用一层可选目录；企业里按团队/项目划分
区域Region应用、数据、服务所在的物理位置（数据中心）；子账户一旦选好区域，资源就落在那里，与你的所在地无关。课程示例使用 ap10（https://api.cf.ap10.hana.ondemand.com，见示范项目 README 的 cf login 命令）
权利Entitlement「你有权使用某个服务计划」这件事本身，由服务计划 + 配额构成；从全局账户分配到子账户后才能消费。① 里为本课程开通 hana、xsuaa、destination 等服务的使用权
配额Quota权利上的数量上限（实例数、内存、调用量…）；它决定你能创建几个实例，不是能不能用。试用账号的配额由 SAP 设定、会调整 ~；超额会在创建实例时报错，通常只说计划不可用
角色集合Role Collection一组应用角色的集合，直接分配给用户；用户拿到的权限最终体现在 JWT 的 scope 里。部署后把 OrderAdmin 角色加进一个角色集合并分配给测试用户，才能提交订单（⑧）
角色（应用角色）Role — 由 Role Template 实例化而来角色模板在具体应用实例上实例化成的角色，内含若干 scope；它是「角色集合」的组成单位。xs-security.json 里定义模板 OrderViewer / OrderEditor / OrderAdmin
权限范围Scope最小的权限名字（如 $XSAPPNAME.submit）；写在 JWT 里，CAP 的 @requires/@restrict 就是按它判断。xs-security.json 的 3 个 scope：view / edit / submit（放行提交订单靠它）
信任配置Trust Configuration子账户里「本子账户信任谁来登录」的配置页面：默认信任 SAP ID service，也可以建立对自定义 IdP 的信任。①「成员与权限」一节的手顺：先按默认 IdP 走通，再考虑换企业 IdP
身份提供者IdP — Identity Provider负责验证用户身份的一方；SAP BTP 的默认 IdP 是 SAP ID service，企业环境通常是 SAP Cloud Identity Services（IAS）或公司的 AD/Entra ID。本地开发不需要 IdP（用 mocked 假用户）；部署后才真正经过 IdP 登录（⑧）
授权与信任管理服务XSUAA — SAP Authorization and Trust Management service（技术名 xsuaa）子账户里的 OAuth 2.0 授权服务器：向 IdP 认证用户、签发 JWT、把 xs-security.json 的 scope 映射进 token，并提供 approuter 要用的 client 凭据。mta.yaml 的资源 demo-node-uaa（service: xsuaa，path: ./xs-security.json）
目标（目的地）Destination — Destination service（技术名 destination）保存「怎么访问某个远程服务」的配置（URL、认证方式、代理类型…），应用按名字取用，避免把地址写死在代码里。mta.yaml 里 approuter 的 destinations 组（把 srv-api 的地址注入 xs-app.json 的路由）
连接性服务Connectivity — Connectivity service（技术名 connectivity）跨网络连接能力：云上应用经它（配合 Cloud Connector）访问本地系统，也用于云间连接与代理。本课程示范项目是纯云上服务，未使用（接本地 S/4 时才需要）
云连接器Cloud Connector装在本地网络里的代理：把本地系统「暴露」给指定子账户，并做资源级访问控制与审计。本课程未实测（无本地系统）；概念与手顺位置见 ①
Cloud Foundry 组织Cloud Foundry Org在子账户里启用 Cloud Foundry 环境时自动创建的组织，与子账户是 1:1 关系（名字可以不同）。cf target 输出的 org（课程手顺里的完成判据）
Cloud Foundry 空间Cloud Foundry Space组织下更细的分区，真正部署应用与创建实例的地方；权限、实例、配额都按空间隔离。课程里建 dev 空间；mta.yaml 的 ${org}-${space} 参与 xsappname 生成
服务实例Service Instance「一个具体的服务资源」（一个 HANA 实例、一个 XSUAA 实例…），由服务 + 计划 + 参数创建而来。demo-node-db（hana / hdi-shared）、demo-node-uaa（xsuaa / application）
服务绑定Service Binding把服务实例与某个应用连起来的动作；绑定才会把凭据注入应用（本地是 cds bind，云端由部署时自动建）。本地：cds bind -2 <已部署的 hana 实例名>（把本地运行指向云端 HDI 容器）；云端：MTA 部署时按 requires 自动绑定
服务凭据环境变量VCAP_SERVICESCloud Foundry 注入应用进程的 JSON 环境变量，内容就是所有绑定服务的凭据与元数据；CAP 启动时读它来接数据库、XSUAA 等。部署后用 cf env <srv 应用名> 能看到；本地开发时由 cds bind 生成的私密配置（.cdsrc-private.json）替代
应用路由器Approuter — SAP Application Router（@sap/approuter）Node.js 写的统一入口：做登录跳转与 JWT 校验、按 xs-app.json 把请求转发给后端、也能托管静态内容。demo-node-approuter 模块 + approuter/xs-app.json（authenticationType: xsuaa）
HTML5 应用仓库HTML5 Application Repository（技术名 html5-apps-repo，计划 app-host / app-runtime）存放并分发 HTML5（UI5 / Fiori）静态内容的服务；运行时通常由 approuter 去取用。本课程把 Fiori 应用直接放在 app/book-orders/webapp/，未上仓库（上 Work Zone 时才需要）
多目标应用MTA — Multi-Target Application一份部署描述（mta.yaml）：把多个模块（服务、approuter）与所需资源（HANA、XSUAA）声明在一起，按依赖顺序部署。project-code/demo-node/mta.yaml（2 个 module + 2 个 resource）
MTA 归档MTAR — MTA Archive（.mtar）构建生成的可部署产物：一个带部署描述与全部模块内容的压缩包，由 cf deploy 上传。mbt build -t mta_archives → mta_archives/demo-node_1.0.0.mtar → cf deploy … -f（全链路见 ⑩ 构建与部署）
业务应用工作室BAS — SAP Business Application Studio云上 IDE（VS Code 血统），预装了 CAP / Fiori / Java 等场景所需工具，可终端操作、可调试、可直接部署。课程板块 ② BAS 环境：创建 Dev Space、跑 cds init、端口转发与调试
开发空间Dev SpaceBAS 里的开发环境实例，像一台隔离的云虚拟机：按类型预装工具与运行时，可设内存大小、可停止以省资源。② 的「创建 Dev Space 与内存配额」一节（内存给太小会装不上依赖）
三个最容易搞混的「谁负责什么」
  • 谁校验密码：IdP。谁签发 token、把角色变成 scope：XSUAA。谁执行授权判断：CAP 运行时（读 @requires/@restrict）。
  • 谁能改 JWT 里的 scope：只有 XSUAA（管理员在 cockpit 分配角色集合间接影响）。应用代码不能。
  • 凭据从哪来：本地 cds bind（写 .cdsrc-private.json），云端 VCAP_SERVICES。两边都不该把凭据写进 Git。

4. Node 与 Java 运行时对照术语表

同一份 .cds 模型，两个运行时（Node 侧实做见 ⑤ Node 服务，Java 侧见 ⑥ Java 服务）。下表左边是对照项（带锚点），中间两列是两边各自的术语，最后一列是「真正的差别与坑」——这是换运行时最容易吃亏的地方。

对照项Node.js 侧Java 侧差别与注意点
实现单元模块（module.exports = class … extends cds.ApplicationService）Bean（Spring 容器里的组件，@Component @ServiceName("BookOrderService")）Node 靠「文件位置 + 命名约定」自动装配（srv/ 下的同名 .js）；Java 靠依赖注入，类名与文件名无关，@ServiceName 必须写对
依赖与构建工具npm（npm install / npm ci，锁文件 package-lock.json）Maven（mvn package，锁信息在 pom.xml 的依赖坐标里）npm 可以「先装后锁」，Maven 的版本必须在 pom.xml 声明；CI 里 Node 用 npm ci，Java 用 mvn -B package
工程描述文件package.jsonpom.xml两者都既是元数据又是脚本入口：Node 的 scripts 对应 Java 的 mvn <plugin>:<goal>
运行时配置package.json 的 cds 段（本项目配 sqlite 与 mocked 认证）application.yaml（在 srv/src/main/resources/）同一份配置在两边是两套格式，Go 云端时还要配合绑定；换运行时配置不能照抄
handler 注册方式代码里调用：this.before(...) / this.on(...) / this.after(...)注解声明：@Before(event=…, entity=…) / @On(…) / @After(…) 加在方法上语义一致但出错方式不同：Node 写错实体名是运行时无效果，Java 写错注解值可能直接起不来
实现放在哪与 .cds 同名的 .js（srv/book-order-service.js 配 srv/book-order-service.cds）普通 Java 类实现 EventHandler，用 @ServiceName 指向服务Node 的「同名文件」约定最省事，但改名会静默失联；Java 的类放哪都行，但必须被扫描到
类型系统JavaScript 动态类型；需要类型可用 cds-typer 生成 .ts 声明 ~Java 静态类型；mvn compile 后在 srv/src/gen/java 生成访问器接口与常量Java 在编译期能查出「字段名写错」，Node 只会在运行时返回 undefined——这是两边最大的体验差
查询 APIcds.ql：SELECT.one.from(BookOrders).where({ orderNo })、UPDATE(...).set(...)com.sap.cds.ql：Select.from("BookOrders")…，再交给 CqnService.run(query)都是构造 CQN；Node 的 fluent API 更短，Java 的泛型更安全。聚合写法：Node 用 .columns('sum(amount) as total')
事件上下文req（cds.Request）：req.data、req.params、req.user、req.rejectEventContext（如 CdsCreateEventContext）：context.getCqn()、context.getTarget()Node 的 req 是「一个对象什么都有」；Java 按事件类型分多个上下文类，取参数要选对类型
业务错误返回req.reject(409, '订单号 … 已存在')抛 ServiceException／写入 messages 后返回 4xx ~两边都要保证状态码是 4xx：未捕获异常在 Node 是 500，在 Java 也可能变成 500，测试里必须断言状态码
事务cds.tx / cds.context；handler 内的读写默认同事务与 Spring 事务集成（@Transactional）；SDK 管理请求级事务 ~「明细写入 + 父表合计回写」必须在同一事务里，否则会出现「明细存了、合计没更新」的脏数据
本地数据库@cap-js/sqlite（本项目 db.sqlite，cds deploy --to sqlite:db.sqlite）默认内存数据库 H2（可配持久化 / SQLite）~本地库只是开发便利：上线一律 HANA Cloud。数据库方言差异会暴露写法问题（如 localized 的会话语言）
启动与热重载npm start（cds-serve）、cds watch（改模型自动重启并重编译元数据）mvn spring-boot:run、mvn cds:watch（内含 CDS 构建）Node 的 cds watch 是「零配置看效果」的首选；Java 侧 mvn cds:auto-build 用来在 IDE 外持续重建
测试框架mocha + chai + cds.test（本项目 test/odata.test.js，?cds.test 起真服务）JUnit 5 / Spring Boot Test：@SpringBootTest + @AutoConfigureMockMvc 打 HTTP 层思路一样：起真实运行时打接口。Node 的 cds.test 没有 1:1 的 Java 对应物，Java 侧用 Spring 的测试设施 ~
构建与部署产物cds build --production → gen/srv + gen/db，用 nodejs_buildpackMaven 打包 → srv/target/*.jar，用 SAP Java buildpack ~MTA 里的模块 type 不同（nodejs 与 java），构建命令也不同（npm-ci 与 Maven）；内存/磁盘配额要分别设
共享的东西同一份 db/ 与 srv/*.cds；同一份 xs-security.json；同一个 OData 契约这正是 CAP 的核心卖点：模型与运行时解耦。所以「Node 写一遍、Java 写一遍」不是重复劳动，而是验证模型是否真的中立
生态与扩展npm 生态（中间件、@cap-js/* 插件）Maven + Spring 生态（DI、AOP、安全、可观测库）Node 起步快、依赖杂；Java 工程规范强、样板多。团队能力决定选哪个，不是性能

5. SAP 生态对照表（面向 ABAP 背景）

如果你从 ABAP 世界来，最容易犯的错是「用 ABAP 的词解释 CAP 的对象」。下表给的是对应关系（不是等价物）：左边是你在 ABAP 里的熟面孔，右边是 CAP 里的对应写法，最后一列说明哪里不能照搬。

概念ABAP 侧CAP 侧不能照搬的地方
编程模型RAP — ABAP RESTful Application Programming ModelCAP — SAP Cloud Application Programming ModelRAP 运行在 ABAP 平台（S/4HANA 内外皆可），对象是 ABAP 对象；CAP 运行在 BTP（Node/Java），对象是文本文件。两者解决的问题相似，但产物与生命周期完全不同
行为定义BDEF — Behavior Definition（在 ADT 里创建）服务定义里的 actions { … } + 事件处理器代码CAP 没有单独的「行为定义对象」：动作/函数写在 CDS 里，逻辑写在 .js/.java 里，两者靠名字关联
行为定义语言BDL — Behavior Definition Language（写 BDEF 的语法）CDS 注解 + handler 注册（this.before/on/after）BDL 里能声明 draft、determine、validation、CRUD 开关；CAP 里对应能力散落在「注解 + 代码」两侧，没有统一的 BDL 文件
CDS（ABAP 侧）ABAP CDS — 视图实体（DDL）/ 表函数 / 层次CAP CDS — db/schema.cds + srv/*.cds同名不同物：ABAP CDS 是 DDIC 对象（DDL 源在 ABAP 系统里，靠传输带走）；CAP CDS 是项目文件（靠 Git 与 MTA 部署）
行级授权DCL — Data Control Language（DEFINE ROLE …）@restrict 的 grant / to / where + xs-security.jsonDCL 的 PFCG 条件基于 ABAP 授权对象；CAP 的 to: 是 BTP 角色（最终落实为 JWT 的 scope），两边授权凭据体系不同
数据库过程AMDP — ABAP Managed Database Procedures（METHOD … BY DATABASE PROCEDURE FOR HDB）HANA 原生对象（hdbtable / hdbview / SQLScript 文件）+ CDS 视图CAP 侧把「推下数据库」交给 HDI 部署的对象与 CDS 编译产物；不要把 AMDP 思路直接搬成 CDS 里的魔法，先看能否用视图与 $apply 聚合解决
数据字典SE11 — ABAP Dictionary（表、视图、类型）db/schema.cds + cds deploy（HDI 部署器建表）CAP 里没有 DDIC：表由模型编译出来，改模型 = 改表结构（.hdbtable 迁移），审核方式从「激活」变成「看编译产物与迁移」
开发工作台SE80 — Object Navigator（经典对象树）项目目录：db/ srv/ app/ + VS Code / BAS 文件树CAP 没有「对象列表」这一层：一个文件里可以有多个实体。靠目录约定与 Git 组织，不靠对象仓库
激活 / 编译激活（Activate）DDIC 与 CDS 对象cds compile / cds build（编译期检查模型与注解）CAP 的编译是构建步骤而非平台动作：编译失败不会「半激活」，但你要自己把编译放进 CI，否则错误留到部署才暴露
传输与发布CTS — Change and Transport System（传输请求 STMS）MTA（mta.yaml）+ mbt build + cf deploy传输请求是「系统到系统」的对象搬运；MTA 是「构建产物到空间」的部署，版本化与回滚方式都不同（MTA 回滚用 cf deploy 指定旧包，见 ⑩ 构建与部署）
版本管理abapGit / gCTS（Git 化的 ABAP 对象）原生 Git 仓库 + CI/CD 流水线CAP 里 Git 就是唯一真相源；ABAP 侧 Git 是「导入导出」的桥。在 CAP 项目中不要用「共享开发机当真相源」的做法
编号生成SNRO — 编号范围对象（Number Range）服务端编号生成：max(orderNo) + 1（本项目 nextOrderNo()）SNRO 有数据库级锁与缓冲；max+1 简单但不抗并发。生产上要么用数据库序列/唯一约束 + 重试，要么靠编号服务，别把教学写法当结论
用户与权限分配SU01 用户 + PFCG 角色 + 授权对象IdP 用户 + Role Collection / Role / Scope（cockpit 里分配）BTP 的权限是 JWT 里的 scope，不是运行时查表；所以「临时加个权限」要重新登录（拿新 token），不像 SU01 那样立刻生效

7. 易混词对照

每组给「区别一句话」与「选错会怎样」。这些后果都是课程里真实遇到过的，不是假设。

对照区别一句话选错会怎样
Association vs Composition关联只是「有关系」（查询时 join）；组合是「包含」（父侧生成 FK 列、父删子删、子表依附父表的文档结构）。用 Composition 播种 CSV 时，父侧 FK 列不会被 CSV 填充 → $expand=items 返回空数组（本项目实测因此改用普通 FK + 显式 to-many 关联）。
Action vs FunctionAction 有副作用（POST，可无返回值）；Function 无副作用（GET）且必须有返回值。用 Function 做状态迁移：语义上客户端可以缓存/重试 GET，Fiori 的行内按钮也不会正确触发；反过来用 Action 做「只读的聚合计算」会平白多出写权限风险。
draft 草稿 vs 直接写 activedraft 先写草稿表、点保存才 draftActivate 落库；直接写入立刻生效。给需要「先编后提交」的 UI 用直接写入：用户改一半就被别人看到，且没有并发保护；反过来给简单维护类实体开 draft：凭空多出草稿表与「重复激活 409」的坑。
@readonly vs @restrict@readonly 是「谁都别想写」（等价 grant: 'READ'，to: 'any'）；@restrict 是「谁能写/能读哪些行」。用 @readonly 当权限：任何登录用户照样能读全部数据（只读不等于受限）；只加 @restrict 想实现只读：忘了 grant: 'READ' 会导致连读都被拒（403）。
mocked vs dummy 认证mocked 按配置的假用户校验 Basic 并给出角色；dummy 直接放行特权用户（什么都为真）。用 dummy 测「匿名必须 401」：永远是 200，认证类断言全部失效（本课程明确要求认证测试保持 mocked）。
bound action vs unbound actionbound 写在实体里、URL 带实例键（对「哪一张订单」操作）；unbound 写在服务层、不依赖实例。把「单张订单的状态迁移」写成 unbound：调用方必须自己传 ID，越权风险上升，Fiori 也无法把它作为行内/页面动作绑定到当前上下文。
aspect vs entityaspect 是被 include 的字段集合（编译时展开，不建自己的表）；entity 会建表。以为 aspect 是「父类」去找它的表：找不到；反过来把 managed 当成「只加元数据不进数据库」：DDL 里其实多了 4 列，插入数据时才会发现列不匹配。
cuid vs managedcuid 只给一个 key ID : UUID；managed 给 4 个审计列，不含主键（所以常写成 : cuid, managed）。只 include managed 就以为有主键：实体没有主键，OData 暴露时直接报错；以为 cuid 会送审计列：查不到 createdAt。
projection vs viewas projection on 面向服务暴露（可挑元素、挂 UI 注解）；as select from 是 db 层的查询对象。两张投影源自同一底层实体时忘了 @cds.redirection.target：编译报 can't auto-redirect BookOrders:items（本项目真实报错）。
CSN vs CQNCSN 是模型（JSON，描述有哪些实体与元素）；CQN 是查询（对象，描述要取什么）。排错时找错文件：改模型却盯着 CQN 日志看，或反过来用 CSN 去推断某次请求查了什么字段，结论必然是错的。
$expand vs $select$select 挑字段；$expand 读关联集合（一次请求把子表带出来）。把子表当字段：?$select=items 取不到数组（400 或空）；该展开的没展开：前端出现「明细为空」，而后端其实有数据（或每行再发一次请求）。
EDMX vs CSNEDMX 是对外元数据（含注解，客户端据此生成模型）；CSN 是内部模型（含类型与持久化细节）。用 CSN 当「接口文档」给前端：前端看不到 OData 的动作/函数与 UI 注解；用 EDMX 判断物理列：拿不到表名与列类型。
Service Instance vs Service Binding实例是「资源本身」（一个 HANA / 一个 XSUAA）；绑定是「把凭据交给某个应用」。只创建实例不绑定：应用进程里没有对应的 VCAP_SERVICES 条目，启动时报「找不到数据库/认证凭据」；本地开发忘了 cds bind 也一样。
Entitlement vs Quota权利是「有没有权用这个服务计划」；配额是「最多能用多少」（实例数、内存、调用量）。以为「子账户里能看到这个服务」就等于能用：创建实例时才因权利未分配或缺配额而失败——报错信息往往只说 plan 不可用，容易误判成区域/拼写问题。
namespace vs @pathnamespace 管模型命名与物理表名；@path 管服务 URL。想改 URL 却动了 namespace：表名全变，需要重新部署/迁移数据；反过来想改表名却改 @path：数据库毫无变化。
cds deploy（本地）vs cf deploy（云端）前者把模型落到本地 SQLite（或经绑定落到 HANA）；后者把 .mtar 部署到 CF 空间并创建/更新服务实例与绑定。本地改完模型直接 cf deploy：忘了 cds build 时部署包里的模型是旧的；只跑 cds deploy 又以为「云上更新了」——云端 HDI 容器的表结构根本没动。

8. 本节测试

六道题，覆盖本页三块内容。前两题考缩写，后四题给场景选术语；答完可以回到对应表格核对。

本节测试
  1. 写出下列缩写的英文全称，并各说一句它在 CAP 里的作用：CSN、CQN、EDMX、VCAP_SERVICES。
  2. 把中文名译回英文术语：切面（可被实体 include 的字段集合）、绑定动作、权利、服务绑定、目标（目的地）。
  3. 场景：你要给界面返回「每张订单的明细行数」这类聚合结果，结果集没有主键。应该用 entity、projection 还是 function 暴露？为什么？

  5. 场景：子账户管理员说「我们已经买了 HANA Cloud，为什么你建实例还报错？」请用两个术语把原因说清楚（提示：一个讲「有没有权」，一个讲「能用多少」）。
